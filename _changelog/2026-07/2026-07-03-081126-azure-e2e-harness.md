# Azure Live E2E Harness on the Shared Framework

**Date**: July 3, 2026
**Type**: Feature
**Components**: Testing Framework, Azure Provider, Build System

## Summary

Azure now has a live, dual-engine end-to-end test harness -- the same
provider-agnostic framework AWS, Kubernetes, and Auth0 already run on. It stands
up a real Azure resource, verifies it through the Azure SDK, tears it down, and
confirms removal, on BOTH Pulumi and OpenTofu. `AzureResourceGroup` is wired as
the walking skeleton and passes all six lifecycle phases live against a real
subscription. This is the quality backbone every future Azure kind builds on:
no Azure module is "done" until it proves itself here.

## Problem Statement / Motivation

Every other provider with real infrastructure had a live E2E harness; Azure did
not. Without one, Azure module correctness could only be argued, never proven --
unacceptable for the open-source IaC surface that strangers run against their own
production clouds. The shared framework (`e2e/framework/*`) already provides
dual-engine execution, FK resolution, output verification, and dependency chains;
Azure only lacked its provider harness (`aa_e2e/`) and a first wired kind.

## Solution / What's New

### The Azure provider harness

`apis/dev/planton/provider/azure/aa_e2e/` implements the framework's `Harness`
interface, mirroring the AWS harness's shape:

- `harness.go` -- `Setup` resolves the subscription/tenant (env vars, else
  `az account show`), exports the `ARM_*` environment both engines read, validates
  the ambient credential chain with a zero-permission ARM-token acquisition (the
  Azure analog of `sts:GetCallerIdentity`), and skips per-apply resource-provider
  registration for the ephemeral run (see Implementation Details). `VerifyDeployed`
  / `VerifyDestroyed` dispatch to per-kind verifiers.
- `verify/verifier.go` + `verify/resource_group.go` -- the verifier registry and
  the first verifier, which checks a resource group via `ResourceGroupsClient.CheckExistence`
  (a purpose-built boolean HEAD).

Credentials are never plumbed through the IaC input: the framework passes a nil
provider config, so modules resolve from the ambient chain (an `az` login locally,
OIDC federation in CI) -- no stored secret.

### Walking skeleton + entrypoint

- `azureresourcegroup/v1/e2e/profile.yaml` + `scenarios/minimal.yaml` -- the
  kind's E2E profile and minimal scenario.
- `e2e/azure/azure_test.go` -- `//go:build e2e` entrypoints
  (`TestAzureResourceGroup_Pulumi` / `_Terraform`) driving the shared runner.

## Implementation Details

### Azure resource-provider registration (the one real Azure friction)

By default both engines' Azure providers auto-register a broad set of resource
providers (Microsoft.Compute, .Storage, .Web, ...) at provider init, firing the
registrations concurrently. Azure serialises subscription-level writes and returns
HTTP 409 `ConflictingConcurrentWriteNotAllowed` on a subscription whose providers
are not yet registered -- reproduced live: a resource-group apply failed after
~4.5 minutes of the provider's own retries.

Resource-provider registration is a one-time **subscription bootstrap**, orthogonal
to whether a module creates its resource correctly (the contract E2E validates).
The harness therefore exports `ARM_SKIP_PROVIDER_REGISTRATION=true` for the
ephemeral run -- a single env var both engines honor (azurerm v4 reads it; its
provider-block analog is `resource_provider_registrations = "none"`; pulumi-azure
classic reads it when the builder leaves the arg unset). This keeps the opt-out
scoped to the test harness and touches no production module or shared builder. The
production-module grain decision (adopt `resource_provider_registrations = "none"`
catalog-wide) is recorded for the provider-auth standardization work.

### azurerm v4 requires an explicit subscription

azurerm v4 no longer infers the subscription, so the harness exports
`ARM_SUBSCRIPTION_ID` (and `ARM_TENANT_ID`) in `Setup`. The framework forwards the
process environment to both engines (the Pulumi runner inherits `os.Environ()`; the
Terraform path layers extracted vars on top), so no framework change was needed.

### Dependencies

Adds `github.com/Azure/azure-sdk-for-go/sdk/{azcore,azidentity,resourcemanager/resources/armresources}`
(azcore/azidentity were already in the graph at their existing versions; only
armresources plus its standard transitive set is genuinely new). `MODULE.bazel`
and BUILD files regenerated via `bazel mod tidy` + Gazelle.

## Verification

- Offline: targeted `go build` of the harness and the walking-skeleton module, the
  release-equivalent Pulumi build, `go vet`, e2e-tagged test compile, and the
  repo-wide `make build-go` -- all green.
- Live dual-engine (ephemeral create -> verify -> destroy against a real test
  subscription, resource group deleted on teardown, zero orphans confirmed):
  - `TestAzureResourceGroup_Terraform/minimal` -- all 6 phases PASS (~93s).
  - `TestAzureResourceGroup_Pulumi/minimal` -- all 6 phases PASS (~74s);
    outputs transform reported 3/3 proto fields populated.

## Benefits

- Azure module correctness is now provable, not asserted -- the backbone for the
  Azure catalog rebuild.
- The harness is a thin verifier package on the shared framework; adding a new
  Azure kind's E2E is a verifier + a scenario YAML + two test entrypoints.

## Impact

Affects Azure E2E only. No production module behavior changes; the walking-skeleton
`AzureResourceGroup` module was adopted onto the shared pulumi provider builder
independently (via the merge of the OIDC-adapter work). No CI workflow yet -- an
`e2e-azure.yaml` follows once Azure OIDC federation for CI exists, mirroring the
AWS workflow's shape.

## Related Work

Follows the AWS E2E harness pattern; consumes the shared `e2e/framework/*` and the
merged Azure pulumi provider builders (`pulumiazureprovider` / `pulumiazurenativeprovider`).

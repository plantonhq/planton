# The operator signs in to the bundled vault as itself and hands the control plane a scoped token it keeps alive and re-issues after a restore

**Date**: September 15, 2026
**Type**: Feature
**Components**: The Planton operator (the OpenBAO component, its resources and bootstrap client, the control plane's binding, the janitor's record, the README, the definition's type comment), the real-server proofs under `requires_docker`

## Summary

Until now the control plane signed in to the bundled vault with the vault's root token, read from the operator's init Secret -- and after a restore that Secret is gone, so a restored vault (which the previous two changes made open itself) would stand open and unusable. Nothing running signs in with the root token any more. At initialization the operator enables the vault's Kubernetes auth method, writes two policies and two roles, and from then on signs in on every pass as its own ServiceAccount: a session created for the pass and revoked when it ends, never stored. The vault verifies that sign-in with the cluster through its own ServiceAccount, which the operator grants the cluster's `system:auth-delegator` role by a ClusterRoleBinding applied as a platform satellite (labeled with the platform's UID, collected by the janitor when the platform is gone). The control plane gets a token of its own, minted through a token role and limited to the `secret/` and `transit/` engines, into `<platform>-openbao-token`: the operator looks it up by its accessor every pass, renews it when less than half its seven-day period is left, mints a new one when the Secret is missing or the token is no longer valid (a platform restored into a fresh namespace, a token somebody revoked, an operator away longer than the period), and rolls the control plane on the new accessor. The root token stays in the init Secret as the break-glass, and the operator uses it for exactly one thing: repairing its own sign-in when the vault does not know its current identity.

Every way the sign-in can fail is a sentence: the vault refuses the operator's identity and no root token is at hand (the identity the operator has, the binding to check, the two ways back); the root token in the init Secret no longer works (how to mint a new one with the recovery quorum); the role is right and the login still fails (the binding and the API server's name). An open vault whose init Secret has gone missing is no longer refused -- nothing running needs that Secret -- but a working platform with the hazard named in its Ready sentence: the break-glass gone under a cloud seal, the next restart unopenable under the built-in one. And the vault's PostgreSQL connection now reaches the server as the driver's own environment (`PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGSSLMODE`, `PGPASSWORD`) with no connection URL anywhere, the way the catalog's standalone vault hands its connection over.

## What Changed

### The access arrangement, in one place

`operator/internal/resources/openbao_auth.go` (new): the mount path (`kubernetes`), the API server as every cluster names it (`https://kubernetes.default.svc:443` -- stored in the vault's data and true on whatever cluster a restored vault runs in), the operator's session TTL (ten minutes), the control plane's token period (seven days), the names (`<platform>-operator` for the operator's auth role and policy, `<platform>-control-plane` for the control plane's token role and policy, `<platform>-openbao-token` with keys `token` and `accessor`, `<namespace>-<platform>-openbao-auth-delegator` for the grant), the two policies as text (`OpenBAOControlPlanePolicy`: the two engines, every capability but sudo, nothing under `sys/` or `auth/`, scoped to the mounts because the platform releases independently of the operator and a verb-by-verb policy would make every new use of the vault a forced operator release; `OpenBAOOperatorPolicy`: the engines' mounts, its policies and roles, minting and accessor operations through the role, never the engines and never a sudo path), the token Secret's note, and `OpenBAOAuthDelegatorClusterRoleBinding` in the control plane's token-reviewer grant's shape.

`operator/internal/bootstrap/openbao_auth.go` (new): the raw-API helpers -- `EnableKubernetesAuth` (idempotent; sudo, so root at initialization), `Read`/`WriteKubernetesAuthConfig`, `Read`/`WriteKubernetesAuthRole`, `KubernetesLogin`, `Read`/`WritePolicy`, `Read`/`WriteTokenRole`, `CreateTokenWithRole`, `LookupAccessor` (not found for a revoked or expired token), `RenewAccessor`, `RevokeAccessor`, `RevokeSelf`; `APIError` carries the server's status and words, with `IsPermissionDenied` and `IsNotMounted`. `EnsureOpenBAOMounts` takes any token.

## Why

A restore is whole only if the restored vault can be used, and until now the only credential that could use it died with the platform. The operator's own sign-in survives any restore because it is an identity, not a stored value; the control plane's token is re-issued by the thing that issued it. The root token -- the most powerful credential in the install, until now in daily use by the control plane -- is now used by nothing running, and the operator's own power over the vault lives in a session minutes long that is never written anywhere. The control plane's policy is scoped to the two engines rather than today's verbs on purpose: the platform and the operator release independently, and the boundary that matters is that the control plane can reach nothing outside its engines.

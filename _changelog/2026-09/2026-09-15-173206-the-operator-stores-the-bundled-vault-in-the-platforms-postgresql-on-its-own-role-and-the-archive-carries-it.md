# The operator stores the bundled vault in the platform's PostgreSQL, on its own role, and the archive carries it

**Date**: September 15, 2026
**Type**: Feature
**Components**: The Planton operator (the OpenBAO and PostgreSQL components, the vendored OpenBao chart, the operator's RBAC and README), the public self-hosting backup page

## Summary

The self-hosted platform's bundled vault used to keep its data on a volume of its own, outside the platform's backup, so a restored platform came back with an empty secrets manager. The operator now runs the vault against the platform's PostgreSQL: the database component declares a least-privilege role and a database for it through CloudNativePG (a managed role whose password lives in an operator-owned basic-auth Secret; a `Database` object owned by that role -- both of which converge on a restored cluster, where CloudNativePG resets the role's password to the Secret's value exactly as it does the superuser's), and the vault component derives the connection URL from that Secret and hands it to the server as the environment variable OpenBao's backend reads first, never through the configuration the chart renders into a ConfigMap. The vault has no volume; it waits for its role and database in CloudNativePG's own words before it starts; the chart pin moves from 0.25.6 to 0.28.6 (OpenBao v2.6.1, the standalone vault kind's pin); `status.backup.vault` says whether the archive covers the vault, which seal opens it, and which Secret to keep; and a vault that comes back from an archive initialized and sealed with no keys Secret is refused in words that name the Secret, its keys, the archive, and the two ways out.

## What Changed

### The database component provisions the vault's role and database

`internal/resources/postgresql.go`: `PostgreSQLVaultRole` (`openbao`), `DBOpenBAO` (`openbao`), `PostgreSQLVaultRoleSecretName` (`<cluster>-openbao`, the shape CloudNativePG's own `-superuser` Secret has), `PostgreSQLManagedRole` rendered as `spec.managed.roles[]` (a login role with no cluster-wide privilege), and `NewPostgreSQLDatabase` -- a `postgresql.cnpg.io/v1 Database` with `ensure: present` (idempotent on a restored cluster that already holds it) and `reclaimPolicy: retain` (the data lives and dies with the Cluster, never with the declaration; a platform that later opts the vault out leaves the database standing, deliberately). The one-superuser comment now says what it always pointed at: the vault is the first consumer on its own role and the shape the rest converge on. `internal/component/postgresql.go` ensures the role's `kubernetes.io/basic-auth` Secret (new `Base.EnsureBasicAuthSecret`, create-once, owner-referenced) before the Cluster names it, and applies the `Database` object after the Cluster; RBAC for `databases.postgresql.cnpg.io` in both the generated role and the chart's copy.

### The vault component consumes them

`internal/resources/openbao_helm.go`: chart pin 0.28.6; the config stanza is `storage "postgresql" { max_parallel = "32" }` -- no credential, and one sizing fact: the backend's default pool of 128 open connections would have claimed nearly half of the platform database's 300, which the control plane's pools, Temporal's four services, the identity server, and OpenFGA already share (and which 100 once saturated); `dataStorage.enabled: false` (the chart guards the claim template and the data mount on that one switch); `extraSecretEnvironmentVars` projecting `BAO_PG_CONNECTION_URL` from `<platform>-openbao-storage`; `OpenBAOStorageURL` composes the URL in one place with the platform's in-cluster `sslmode=disable` posture and the password escaped. `internal/component/openbao.go` gains `Dependencies() = postgresql`; `internal/component/openbao_storage.go` waits for the role in CloudNativePG's `managedRolesStatus.byStatus.reconciled` and the database's `status.applied` (relaying `cannotReconcile` causes and the database's `status.message`, since the backend gives up after one failed connect), then derives and applies the storage Secret every pass so it can never drift from the role Secret; the volume plumbing is gone.

### The archive tells the truth about the vault

`internal/component/openbao_backup_status.go`: `status.backup.vault {covered, seal, initSecretName, message}` derived from the declaration and the backup state and attached wherever the PostgreSQL component writes `status.backup` -- the opted-out vault, no backup declared, the built-in seal with the adopter's own Secret (a restore needs it present; keep a copy), the built-in seal with the operator's Secret (deleted with the platform; the honest warning and the two remedies), and every cloud seal (the restored vault opens itself; the Secret is break-glass). The initialized-and-sealed vault whose keys Secret does not exist returns `ConfigurationRefused` with the Secret as its object -- the shape a missing named Secret takes everywhere else -- and a sentence that names the archive it came from when it did.

### The chart pin, with the diff read

0.25.6 to 0.28.6 changes, for the keys the operator sets: nothing. The diff is the injector's `externalBaoAddr` (the injector is off), the CSI image tag, a `tpl` on extra containers, `seccompProfile: RuntimeDefault` defaults, and an external-address helper rename. The image the chart resolves is `quay.io/openbao/openbao:2.6.1`.

### Documents that describe the thing that changed

`operator/README.md`: the backup paragraph's boundary sentence becomes the coverage paragraph; "How It Reconciles" gains the doctrine -- a bundled component's data belongs in the platform's database when the platform already archives it. `site/public/docs/self-hosting/backup-and-recovery.md`: "Not in it: the secrets manager" becomes "Also in it: the secrets manager", with what opens the restored vault and the Secret to keep. `openbao.go`'s comments stop describing a manual-init path and a volume.

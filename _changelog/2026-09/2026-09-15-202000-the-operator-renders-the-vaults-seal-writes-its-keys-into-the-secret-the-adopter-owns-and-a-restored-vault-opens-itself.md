# The operator renders the vault's seal, writes its keys into the Secret the adopter owns, and a restored vault opens itself

**Date**: September 15, 2026
**Type**: Feature
**Components**: The Planton operator (the OpenBAO component, its resources, the bootstrap client, the README, the definition's field comments and the regenerated CRD), the platform kind's `init_secret_name` comment and its regenerated reference page, GUIDE, and preset 06 explainer

## Summary

The platform kind already accepted a seal for its bundled vault and a Secret the adopter owns for the vault's keys; the operator now honors both. It renders whatever seal the declaration chose -- a Google Cloud KMS key, an AWS KMS key, an Azure Key Vault key, or a central OpenBao's transit key -- into the vault's configuration with no credential in it (public identifiers ride plain environment variables, every credential is projected from the Secret the declaration names, keyed by the variable the seal's wrapper reads, and the keyless identity rides the vault ServiceAccount's annotations). It initializes a cloud-sealed vault with a recovery quorum instead of key shares (the server refuses the other shape), never calls unseal on it, and waits for the server's own loop to open it -- after initialization and on every start after, including a restore on a cluster that has never seen the vault. It writes the keys (unseal keys under the built-in seal, recovery keys under a cloud seal -- different words, because recovery keys never open anything) and the root token into the Secret the adopter named, without an owner reference, and never writes over a Secret that already holds a vault's keys. On a restore it unseals a built-in-seal vault from that Secret. And every way the seal can fail is a sentence with the cause and the next step: the credentials Secret missing its key (refused before the chart renders), a seal that differs from the one the vault was initialized under (refused before the chart renders; the seal is decided at creation and the server would refuse to start against its own storage), a crash-looping vault under a seal (the classifier's verdict plus the check the server makes at start -- both Google Cloud roles, the `Error configuring seal` log line), a vault that stays sealed under a cloud seal (opening, for a young pod; the decrypt grant its identity lacks, for an old one), a keys Secret that belongs to another vault, an open vault whose Secret is gone.

Two things about the storage landed with it. The vault's database password reaches its process the way every other consumer of the platform's database receives one -- projected straight from the role's credential Secret as `PGPASSWORD`, with the connection URL a plain variable carrying no password -- and the derived URL Secret is gone. And the promise the adopter-owned keys Secret carries is now stated precisely in every place it was made: the operator never deletes it and deleting the `PlantonPlatform` leaves it standing, but a namespace the declaring resource owns is deleted with that resource and takes every Secret in it, so the copy kept outside the cluster is what a restore into a new cluster needs.

## What Changed

### The seal is rendered from the declaration

`operator/internal/resources/openbao_seal.go` (new): `OpenBAOSealOptions` with one arm per seal, the shape the object stores use -- `Stanza()` (the `seal` block, non-credential parameters only, byte-faithful to the standalone vault kind's rendering), `PlainEnv()` (`AWS_REGION`, an optional `AWS_ACCESS_KEY_ID`), `SecretEnv()` (`AWS_SECRET_ACCESS_KEY`, `AZURE_CLIENT_SECRET`, or `VAULT_TOKEN`, each projected from the named Secret's key of the same name), `CredentialsSecretName()` and `RequiredCredentialKeys()` for the preflight, `Word()`, `Human()`, `Fingerprint()` (the seal word plus the key it names), `DecryptGrant()` and `StartCheck()` per arm for the sentences. `openbao_helm.go`: `OpenBAOHelmValues` takes `OpenBAOHelmOptions{CRName, Namespace, StoragePasswordSecretName, Seal, ServiceAccountAnnotations}`; the stanza is appended to `standalone.config`; `server.extraEnvironmentVars` carries the storage URL and the seal's identifiers; `server.extraSecretEnvironmentVars` carries `PGPASSWORD` from the vault role's Secret and the seal's credential, in a fixed order; `server.serviceAccount.annotations` renders the keyless identity. `OpenBAOInitSecretNote` is written per seal and per owner. The init Secret's keys: `unseal-keys` under the built-in seal, `recovery-keys` under a cloud seal, `root-token` under both; the annotation `planton.ai/openbao-seal` records the fingerprint.

### One initialization path, in the shape the seal requires

`operator/internal/bootstrap/openbao.go`: `InitializeOpenBAO` takes `OpenBAOInitOptions` -- `ShamirInit(shares, threshold)` sends `secret_shares`/`secret_threshold`, `RecoveryInit(shares, threshold)` sends `recovery_shares`/`recovery_threshold` and nothing else, because a server under a cloud seal refuses the other pair ("not applicable to seal type") and forces its own barrier to one share -- and returns `UnsealKeys` or `RecoveryKeys` with the root token. `WaitUntilUnsealed` polls health for the server's own loop, which retries the stored key every five seconds.

`operator/internal/component/openbao.go`: `Reconcile` preflights the seal before the chart renders (`preflightSeal`: the credentials Secret and its key; the declared seal against the fingerprint on the init Secret), renders with the seal, and hands the running server to `ensureInitialized`, whose arms are: not initialized -- refuse a Secret that already holds keys, else init in the seal's shape, write the Secret with a bounded retry, unseal with the shares (built-in) or wait ~8 seconds for the server to open itself (cloud), mount the engines; initialized and sealed -- unseal from the Secret (built-in; no Secret is refused with the Secret named) or report the seal's state by the vault pod's age (cloud); initialized and open -- ensure the engines and re-assert the Secret's note and fingerprint, refusing an open vault whose Secret does not exist with the ways back named. A health endpoint that does not answer goes through the workload classifier -- a crash-looping pod still reports phase Running, and the bare "waiting for health" sentence the component used to return hid every crash-loop behind it -- with the seal's start check appended when a seal is declared.

`operator/internal/component/openbao_init_secret.go` (new): the init Secret's contract -- `initSecretHoldsKeys`, `readInitSecret`, `writeInitSecret` (a create, or a merge patch that fills a Secret the adopter pre-created empty; the adopter's own without an owner reference, the operator's with; deliberately never a server-side apply, so the annotation pass that IS an apply can never drop the data), `ensureInitSecretAnnotations` (the note; a recorded fingerprint re-asserted with its own value, never the declaration's), and the sentences for a Secret holding another vault's keys, a write that failed after init, and an open vault without its Secret. `openbao_seal.go` (new, component): `sealOptionsFrom`, `vaultServiceAccountAnnotations`, `preflightSealCredentialsSecret` (the object-store preflight's wording), `sealChangedMessage`, `sealNotOpenedMessage`, `sealStartHint`, `vaultPodAge`. `openbao_backup_status.go` speaks the resources' seal vocabulary instead of its own. `connection.go`: `OpenBAOConnection` takes the init Secret's name, so the control plane reads its token from the Secret the adopter named.

### The storage password reaches the vault the way every consumer's does

`openbao_helm.go`: `OpenBAOStorageURL` composes the URL with no password; `OpenBAOStoragePasswordEnv` (`PGPASSWORD`) is projected from the role Secret's `password` key -- the projection the identity server already uses for its own `PGPASSWORD` and the control plane for `DB_PASSWORD`. `openbao_storage.go` no longer derives a Secret; `OpenBAOStorageSecretName` is gone.

### The promise the keys Secret carries, stated precisely

`catalog/kubernetes/kubernetesplantonplatform/v1alpha1/spec.proto` (`init_secret_name`; the reference page and the Go stub regenerated), `operator/api/v1/planton_platform_types.go` (`initSecretName`; the CRD and the chart's copy regenerated together), `GUIDE.md`, `presets/06-backups-to-r2.md`: the operator never deletes the Secret and deleting the `PlantonPlatform` leaves it standing; a namespace the declaring resource owns (`create_namespace: true`, which every preset sets) is deleted with the resource and takes every Secret in it; keep a copy outside the cluster, or place the platform in a namespace you own.

### Documents

`operator/README.md`: a `spec.vault` paragraph in "Declaring a Platform" (the seal arms and their identities, the start-time check and both Google Cloud roles, the init Secret's contents under each seal and who owns it, what a destroy does, the never-overwrite rule, the refused seal change) and one sentence in "How It Reconciles" on what is refused before rendering.

## Verification

- `go test ./internal/resources/`: every arm rendered through the real chart -- the stanza in the config ConfigMap with the key it names and no credential parameter, the identifiers as plain variables, the credential projected from the named Secret and never a plain value, the keyless identity on the ServiceAccount, no Secret rendered, no credential parameter anywhere in any rendered document; the storage URL a plain variable with no password and `PGPASSWORD` projected from the role Secret; the note per seal and owner; the seal options' stanza, environment, required keys, fingerprint, and grants.
- `go test ./internal/bootstrap/`: the two init shapes and the refusal of `secret_shares` under a seal; the wait returns on open and on timeout and never unseals.
- `go test ./internal/component/`: on a fake OpenBao and a fake cluster -- fresh built-in seal (operator Secret, owner reference, `unseal-keys`, fingerprint `shamir`), fresh built-in seal with a named Secret (no owner reference), fresh cloud seal (recovery init, no unseal call, `recovery-keys`, the server opens itself), a pre-created empty Secret filled in place, a populated Secret refused for both owners with init never called, a restored built-in-seal vault unsealed from its Secret, a restored one without it refused, a cloud seal that stays sealed (opening for a young pod, the grant for an old one), an open vault without its Secret refused, annotations re-asserted without touching data and a recorded fingerprint kept, the preflight's four verdicts, and a crash-looping pod behind a dead health endpoint classified with the seal clause.
- `go test -tags=requires_docker ./internal/bootstrap/`, against real servers: OpenBao 2.6.1 on PostgreSQL 16 with the password reaching the server as `PGPASSWORD` and a password-less URL, initialized, reopened by a second process on the same database with the first one's keys, mounts intact; a transit-sealed vault against a dev-mode key holder refusing `secret_shares`, initializing with a recovery quorum, opening itself with no unseal call, killed and started again on the same database and seal and opening itself again; a server with a wrong seal token exiting at start with `Error configuring seal` in its log.
- `make -C operator manifests generate fmt vet`; `make -C operator test` (every package, the controller's envtest specs installing the regenerated definition); the e2e package compiled under its tag; `go test ./catalog/kubernetes/kubernetesplantonplatform/v1alpha1/`; `go test ./pkg/explain/refgen/ ./pkg/protodocs/` on the regenerated page and index.

# The standalone OpenBao kind declares a storage engine and a replica count, and drives the chart's mode from them

**Date**: September 15, 2026
**Type**: Feature
**Components**: `catalog/kubernetes/kubernetesopenbao` (the spec and its tests, both IaC engines and the Pulumi module's first tests, the permissions, cost, control, and capacity profiles, the presets and every E2E fixture, the guide and catalog page), `catalog/_patterns/stateful-kind-disaster-recovery.md`, `charts/kubernetes/identity-and-access-platform`, the component update rule, the regenerated reference pages, graph, and cost estimates

## Summary

`KubernetesOpenBao` modeled its server as the Helm chart's mode switch -- `dev`, `standalone` (file storage, one instance), `ha` (Raft, N replicas) -- which fused two facts OpenBao keeps apart and offered, as "the production shape for single-instance installs", the one engine OpenBao's own documentation calls not production recommended. The server now declares what OpenBao has: `dev` for a lab, otherwise a storage engine -- `raft` (integrated storage, the only engine with a snapshot API, its data volume inside the arm because no other engine has one) or `postgresql` (OpenBao's production-ready external backend, declared by reference to the catalog's `KubernetesPostgres` on the same shape eight kinds already carry) -- and `replicas`. Declaring nothing is a single-node Raft server that can be backed up. `standalone` and `ha` are reserved; file storage is not offered.

The chart is told a mode, never an engine: both engines run in the chart's `ha` mode with the engine's stanza in the configuration string the module already writes -- Raft with the chart's Raft toggle on, PostgreSQL with it off, the string in `ha.config`, and no data volume -- and the chart's `standalone` mode is never driven. Both IaC engines render the configuration string and the chart values byte-identically for seven fixtures, and the chart itself renders the expected objects from those values against its own schema. Every rule is keyed on the engine and says what to change.

## What changed

### The contract

`v1alpha1/spec.proto`: `KubernetesOpenBaoServer` keeps `dev = 1` as a plain field, reserves `2, 3, 5` (`standalone`, `ha`, `data_storage`), and gains `oneof storage { raft = 10; postgresql = 11 }` and `optional int32 replicas = 12` (1..11, default 1). `KubernetesOpenBaoRaftStorage` carries the data volume (`KubernetesOpenBaoVolume`, the renamed volume-request message; `audit_storage` stays on the server because the chart claims the audit volume for any non-dev server). `KubernetesOpenBaoPostgresqlStorage` copies the catalog's database-by-reference shape: `host` -> `KubernetesPostgres.status.outputs.rw_service`, `port`, `database`, `username` (default `app`), `password_secret {secret_name -> status.outputs.password_secret.name, secret_key}`, `ssl_mode` (default `require`: OpenBao's backend tries TLS and a `KubernetesPostgres` serves it), and `max_parallel` (OpenBao's default of 128 connections per server exceeds a default PostgreSQL's 100, multiplied by `replicas`). Rules, one root cause each: `spec.server.dev_excludes_storage`, `spec.server.dev_excludes_replicas` (keyed on the value, because the manifest loader fills the declared default before validation), `spec.backup.not_on_dev`, `spec.backup.not_on_postgresql` ("a vault stored in PostgreSQL is backed up by its database"); a volume on the wrong engine is unwritable rather than refused. `auto_unseal.seal` gains `(buf.validate.oneof).required`, the convergence the other two oneofs in the file already had; `spec.restore.requires_auto_unseal` simplifies accordingly. `outputs.proto`: `active_service` exists for every server on a storage engine. 99 spec cases.

### Both engines, byte-identical

The Pulumi module (`locals.go`, `bao_config.go`, `values.go`, `outputs.go`, the new `postgres_env.go`) and the Terraform module (`locals.tf`, `outputs.tf`, the regenerated `variables.tf`) resolve `Dev`, `Storage`, and `Replicas` from the spec and render: Raft -> `ha {raft {enabled, setNodeId, config}}` with `dataStorage` from `raft.data_storage`; PostgreSQL -> `ha {raft {enabled: false}, config}` with `dataStorage.enabled: false`; the stanza `storage "postgresql" { ha_enabled = "true" [max_parallel] }` with no `connection_url` and `service_registration "kubernetes"` for both engines. Three facts read from the OpenBao and pgx source decided the shape:

- **`ha_enabled` is unconditional, one replica included.** The core runs in HA mode only when the backend reports `HAEnabled()`, and the `openbao-active` pod label -- what the chart's `-active` Service selects on -- is patched only from the HA leader path. Without it a one-replica PostgreSQL vault's `active_service` output would name a Service selecting nothing.
- **The connection is the driver's environment, not a composed URL.** OpenBao's backend accepts a blank `connection_url` and its driver (pgx, at the version OpenBao pins) reads `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGSSLMODE`, and `PGPASSWORD` when the string is blank. The five plain facts ride the chart's `extraEnvironmentVars`; `PGPASSWORD` rides `extraSecretEnvironmentVars` from the referenced Secret and key -- the seam the seal credentials already use. Nothing is composed, nothing needs escaping, and the module never holds the password.
- **The PodDisruptionBudget follows the replica count and the engine.** The chart enables its server budget by default and hard-codes `maxUnavailable: 0` for one replica -- a budget that blocks every node drain and cluster scale-down forever while protecting nothing, and the shape a bare manifest now gets. The modules render `ha.disruptionBudget.enabled: replicas > 1`; Raft keeps the chart's quorum arithmetic; PostgreSQL allows `replicas - 1` (the database holds the data; one live node is availability).

The Pulumi module gains its first tests (`render_test.go`): the configuration string, the values switch, the two environment lists, the active Service rule, and a leak gate that proves `PGPASSWORD` appears only as a variable name, the referenced Secret only as a `secretName`, and no credential value or connection URL anywhere the module wrote. The same test writes each fixture's documents to disk on request so the Terraform rendering (`tofu console` over `planton tofu load-tfvars`) can be diffed byte for byte -- seven fixtures (Raft at 1 and 3 with a volume, PostgreSQL at 1 and 3 with every field, dev, Raft with a backup, Raft with an AWS KMS seal) were, on both the configuration string and the values. The backup and restore scripts' sentences name Raft storage (`server.raft`) instead of the retired arm, byte-identical across engines (the parity guard passes).

### Every manifest a gate reads says the new shape

`ha: {replicas: N}` + `dataStorage` -> `raft: {dataStorage}` + `replicas: N`; `standalone: {}` -> `raft` in the five presets, `e2e/manifest.yaml`, seven scenarios and three fixtures, the guide's restore target, the catalog page's example, and the disaster-recovery pattern's embedded vault -- every one validated with the tree-built CLI (the R2 fixtures with their tokens substituted). The identity-and-access-platform chart's `openbao_ha_enabled` / `openbao_ha_replicas` become one `openbao_replicas` (default 1) on `raft` with the volume inside it; the offline chart validator passes all 18 charts. `cost.yaml`, `controls.yaml`, and the capacity derivation re-key on `server.replicas`, `server.raft.data_storage`, and `server.postgresql`; the cost estimates regenerate. `iac/permissions.yaml` gains the `policy/poddisruptionbudgets` rule the chart has always needed in its HA mode and names the discovery Role and RoleBinding that let the server label its pod.

### The teaching

The component update rule gains the timeless lesson: a chart's mode switch is a chart fact; when it fuses facts the software keeps apart, model the facts, drive the mode from them, read upstream's own posture before calling a mode "production", prefer a shape that makes a rule unwritable to a CEL that refuses it, and key a CEL on a defaulted scalar's value, never its presence.

## What did not change here

The verifier's shape extractor and the `postgresql-storage` lane, the guide's engine-choice judgment, the README and catalog page paragraphs that still describe modes, the preset explainers, the pattern's line about what has nothing to snapshot, the eval bank's answer text, the identity chart's PostgreSQL option, and the console -- all follow in their own slices. No live lane ran; `planton tofu plan` / `pulumi preview` against a cluster were not run this session (Docker was stopped on the shared machine mid-session); the chart-render proof above stood in for them.

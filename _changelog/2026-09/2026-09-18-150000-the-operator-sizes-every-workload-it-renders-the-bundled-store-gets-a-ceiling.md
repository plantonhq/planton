# The operator sizes every workload it renders; the bundled store gets a ceiling

**Date**: September 18, 2026
**Type**: Bug fix and hardening
**Components**: `operator/api/v1` (`spec.database.redis`), `operator/internal/resources` (every renderer), `operator/internal/component/redis.go`, `helm/planton-operator` (the CRD copy)

## Summary

A self-hosted Planton installed with `spec.version` alone got a redis-protocol store sized by the Bitnami chart's "nano" preset (a 192Mi limit the chart's own header calls "for basic testing"), no `maxmemory`, `noeviction`, and an append-only file. Thirty-seven hours after a fresh install its dataset reached 158Mi, the pod was OOM-killed, reloaded more persisted data than it may hold, and was killed again, forever, behind a front door still answering 200. Nine of the fourteen workloads the operator renders carried no resource floor at all, so the same class was waiting in every one of them. The store now runs with a 768mb dataset ceiling and `allkeys-lru` eviction under a 1Gi memory limit, persisted so the live build-log stream it also carries survives a restart, and every workload the operator renders carries a sizing the operator chose, declared once as named constants at the top of its renderer with the reason beside it.

## What Changed

- **`spec.database.redis`** gains `persistence` (default on), `maxMemory` (default `768mb`), `maxMemoryPolicy` (default `allkeys-lru`, the kind's eight values), and `resources` (default requests 100m/256Mi, limit 1Gi memory, no CPU limit), in the vocabulary the `KubernetesValkey` catalog kind uses for the same knobs. Defaults resolve in the operator, not in the schema, the way every storage size does. Both CRD homes regenerated; `zz_generated.deepcopy.go` regenerated.
- **The Valkey renderer** takes a `ValkeyHelmOptions` struct (the `OpenBAOHelmOptions` shape) and writes the whole `valkey.conf` it needs (`maxmemory`, `maxmemory-policy`, `appendonly` by posture, `save ""`), names the chart's preset off, and sets the container's resources explicitly. Proven at the render level on the StatefulSet's container and the mounted ConfigMap, in both postures.
- **Persistence stays on by default, a correction to the issue's own fix shape.** The operator wires both `REDIS_CLUSTER_*` and `TEKTON_LOGS_REDIS_*` at this one store, so it holds every live build-log stream until the run archives it; the hosted product already persists exactly that store for exactly that reason. The crash loop was unbounded growth, not persistence; the ceiling is the fix. Flipping `persistence` later is handled in words by the redis component (a StatefulSet's claim templates cannot change in place): it deletes the StatefulSet, and the claim nothing will mount again when persistence was turned off, then the apply recreates the declared shape. The generic apply's Job-only replacement is untouched; the vault's claim is never replaceable by accident.
- **Every workload sized, the house pattern throughout** (requests for CPU and memory, a memory limit, never a CPU limit), each renderer's top `const` block carrying its numbers and the reason, read from a live one-node install before choosing: the control plane (250m/1Gi, limit 4Gi -- the hosted product's pair for the same service; the heap follows from the image's own `-XX:MaxRAMPercentage`), the runner (100m/512Mi, limit 2Gi), the front-door gateway (50m/64Mi, limit 256Mi), the identity server's `ensure-database` init container (10m/32Mi, limit 128Mi), OpenFGA (50m/64Mi, limit 256Mi), Temporal (the four server services 50m/128Mi limit 512Mi with history at 100m/256Mi limit 1Gi; the web UI, admin tools, and schema Jobs 10m/32Mi limit 256Mi), the Barman Cloud plugin (50m/64Mi, limit 256Mi). The console, identity server, OpenBAO, and PostgreSQL floors that already existed inline are lifted into the same shape, unchanged in value. `helmResourceValues` in `helm.go` turns typed quantities into the values shape every chart reads, so a component's sizing is typed Kubernetes quantities whether it renders a Deployment or a chart. Tekton and CloudNativePG ship as vendored upstream releases with their own resources and are not edited.
- **Tests**: `resource_floors_test.go` judges every typed Deployment's container and every chart-rendered container (OpenFGA, all six Temporal workloads, the Barman plugin) by the house pattern at the level Kubernetes sees, so a chart bump that grows a workload fails here; the Valkey render tests assert the container's resources, the mounted `valkey.conf`, and the claim in both postures; the redis component's defaults resolution and the persistence-flip replacement are pinned against a fake client. The boot-contract fixture is untouched (no environment variable changed) and the platform floor stays at `v0.0.65`.

## Verification

`make test` in `operator/` green across every package (the lane regenerates manifests and deepcopy first); `go vet` clean; `make lint` reports no finding in the files this change touched (the lane carries 87 pre-existing findings elsewhere). Met live on 2026-09-18 on a `v0.0.72` instance whose store was recovered by clearing its volume; the first `operator/v0.20.0` apply on that instance is the live proof, and the estate's change record will carry it.

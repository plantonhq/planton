# A workload declares its registry logins on its own spec, and the five workload modules build the image-pull Secret from nothing else

## What changed

- **`WorkloadPod` gains `image_registries`** -- a list of `{server, username, password, email}` logins declared on the workload itself. The five workload kinds (Deployment, StatefulSet, DaemonSet, Job, CronJob) materialize the list into ONE `kubernetes.io/dockerconfigjson` Secret named `<workload>-image-pull` in the workload's namespace, the twin of the `<workload>-env-secrets` Secret they already build from the containers' `env.secrets`, and attach it to the pod beside `image_pull_secrets`. The Secret is created, rolled, and destroyed with the workload. `password` is `sensitive`: a manifest carries only a `$secret/<slug>` reference, resolved inside the deploying infrastructure before the module runs. A server named twice is refused by the spec's own rule (`pod.image_registries.server.unique`) before any plan runs, and the `image_pull_secrets` comment now states the three ways a private image gets pulled and when to use each.
- **The `docker_config_json` IaC input is gone from all five workload kinds, in both engines**, and so is the `kubernetes.planton.dev/docker-config-json-file` annotation that let a module read a docker-config file from the operator's disk. The image-pull Secret's data comes from the spec and from nowhere else: nothing outside the manifest -- not a caller filling an input, not a file on a laptop -- can put a pull credential into a workload's pod. A public image, a same-cloud registry the cluster's own identity reaches, or a Secret declared beside the workload and named in `pod.image_pull_secrets` leaves the module-owned Secret uncreated.
- **A workload container's image has no pull-secret leaf.** `WorkloadContainer.image` is now `WorkloadContainerImage {repo, tag}` (same field number, wire-compatible). The shared `ContainerImage` message keeps its `pull_secret_name` for the kinds whose modules read it as a per-image reference (NATS, RabbitMQ, the Tekton operator, the GHA runner controller, and their siblings); on a workload that leaf was never read, so a developer who filled it got `ImagePullBackOff` with no error. Pull secrets belong to the pod in Kubernetes, and now they do here too.
- **One docker-config encoder.** `pkg/kubernetes/dockerconfigjson` renders the `.dockerconfigjson` document for both the `KubernetesSecret` kind's docker arm and the workload kinds' `pod.image_registries`; the Terraform twins render the same shape and name each other. The `KubernetesSecret` docker password is now `sensitive` (reference-only), its coverage-baseline entry is gone, and the docker-registry preset writes `registryServer` (the field the spec has) with a `$secret/` placeholder -- the preset validates and leaves the preset-validity baseline.
- **The five generated `variables.tf` regenerate from the schema** (`planton tofu generate-variables`): `pod.image_registries` arrives as a typed list, the container images lose `pull_secret_name`, and the hand-written `docker_config_json` variable leaves `locals.tf`. `KubernetesServiceAccount` drops an image-pull-secret entry that resolved to nothing instead of rendering an empty name the API server rejects (both engines).
- **e2e**: `kubernetesdeployment/e2e/scenarios/with-image-registries.yaml` deploys a public image beside a declared GHCR login and proves the module materializes the Secret; every workload kind's offline-proof manifest carries an `image_registries` entry. The five kinds' e2e profiles read `pending_proof` until the kubernetes lane runs the new arm live, and the CI matrix follows.

## Why

A pull credential the platform derives on a workload's behalf can never be honest: the Secret has to outlive the deploy, nobody reviewing the manifest can see it, and the input that carries it is a door any caller can walk through. Declaring the login on the workload puts the credential where every other container-running kind in the catalog already keeps it -- on the spec -- and lets a reader of one manifest answer "how does this pod pull?" without reading anything else.

## How to check

```bash
go test ./pkg/kubernetes/dockerconfigjson/ ./pkg/iac/pulumi/pulumimodule/provider/kubernetes/workloadpod/   # the encoder and the builder, including the duplicate-server refusal
go test ./catalog/kubernetes/kubernetesdeployment/v1alpha1/                                                   # the spec refuses two entries for one server, and an entry missing server/username/password
go run . secret-coverage --check && go run . validate-refs --check                                            # the new password is covered; the docker arm's baseline entry is gone
for k in kubernetesdeployment kubernetesstatefulset kubernetesdaemonset kubernetesjob kubernetescronjob; do (cd catalog/kubernetes/$k/iac/tf && tofu init -backend=false && tofu validate); done
go test ./pkg/iac/moduleverify/ ./pkg/iac/tofu/generators/ ./pkg/explain/refgen/ ./pkg/presetvalidity/       # variables.tf, reference pages, and the preset all agree with the schema
```

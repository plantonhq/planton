# The OpenBao proof surface reads storage engines and gains a PostgreSQL durability lane

**Date**: September 15, 2026
**Type**: Feature
**Components**: `catalog/kubernetes/aa_e2e/verify` (the OpenBao verifier and its dispatch; the CloudNativePG verifier's shared helpers), `catalog/kubernetes/kubernetesopenbao` (a new E2E scenario and its database fixture, the e2e headers and profile, the README and catalog page, a new preset and one explainer, the Pulumi project description), `catalog/_patterns/stateful-kind-disaster-recovery.md`, `charts/kubernetes/identity-and-access-platform`, the eval bank, the regenerated reference page and cost estimates

## Summary

`KubernetesOpenBao`'s server declares a storage engine and a replica count, but the harness that proves the kind still read the retired mode oneof: its extractor looked for `server.ha`, so every re-spelled fixture was read as a single file-storage server and the HA arms were silently dead; and the PostgreSQL engine -- OpenBao's production-ready external backend, declared by reference to a `KubernetesPostgres` -- had no lane at all. The verifier now reads `dev`, the engine, and the count; every server on an engine is read through the `-active` Service the chart's HA mode exports; and a new `behavioral-postgresql` scenario composes a `KubernetesPostgres` beside the vault on the kind cluster and proves the engine's one promise from three witnesses -- no data volume was claimed, the server reports HA on (the lock table is live), the vault's tables sit in the declared database -- before the durability arm shows the secret survives pod loss with nothing on disk.

Every document a person reads about this kind now says storage engines: the README's engine section, the catalog page's opening and its key-configuration bullet, the preset explainers, the e2e headers and profile, the disaster-recovery pattern's line about what has nothing to snapshot, the eval bank's answer. A sixth preset stores the vault in PostgreSQL by reference. The identity-and-access-platform chart gains `openbao_storage`: keep the vault on its own Raft volume, or store it in the chart's own database under the same owner role so one database backup covers identity, authorization, and secrets together.

## What changed

### The verifier reads engines

`verify/openbao.go`: `Mode` becomes `Dev bool` and `Storage string` (`raft` | `postgresql`; unset is Raft), with `PgCluster` and `PgDatabase` read from the PostgreSQL arm. The `-active` Service is asserted for every server on an engine (the module exports it at any replica count), fixtures are presence-only unless dev, and the KV marker is read back through `-active` for every non-dev server. Before that read the verifier waits for the Service to carry an endpoint: `kubectl port-forward` resolves a Service to a pod when it opens, the `-active` selector matches only the pod the server labeled active, and after a pod loss that label lands only once the HA lock is held again -- a tunnel opened early dies with "no pods found" and no HTTP retry gets its turn. The same wait guards the Raft lanes, where the window is narrower.

On PostgreSQL storage, `provePostgresqlStorage` runs between the readiness flip and the round-trip: the `data-<name>-0` claim is absent (the chart claims `data` only for Raft); `sys/leader` on pod 0 reports `ha_enabled` and `is_self` (OpenBao runs HA only when the backend's lock table is enabled and labels its pod active only from the HA leader path -- the same fact the `-active` Service depends on, in the server's own words); and `psql` on the CloudNativePG primary shows `openbao_ha_locks` holding a row and `openbao_kv_store` present in the declared database -- the proof that the `PG*` environment the module renders landed the vault where the manifest said. A host declared literally has no cluster to open; the verifier says so and keeps the server's word.

The CloudNativePG verifier's `currentPrimary` and `psqlDB` are lifted to package-level `cnpgCurrentPrimary` and `cnpgPsqlDB` (the methods delegate), so a kind that stores in a `KubernetesPostgres` never assumes a pod name. `verifier.go` constructs the verifier from the new shape and switches the durability arm on for `behavioral-raft` and `behavioral-postgresql`. `openbao_test.go` pins the extractor on seven shapes in both protojson spellings.

### The PostgreSQL lane

`e2e/prerequisites/kubernetespostgres.yaml` (`e2e-bao-pg`: its own namespace, one instance, `initdb` bootstrapping the `openbao` database under the `openbao` owner -- the operator-maintained `-app` Secret is the password's home) and `e2e/scenarios/behavioral-postgresql.yaml` (the vault joins the fixture's namespace; `host` and `passwordSecret.secretName` by bare reference to the fixture; `replicas: 1`). The CloudNativePG operator arrives through `KubernetesPostgres`'s registry prerequisite edge. One replica is the honest shape on the one-node lab cluster (the chart ships a required hostname anti-affinity; the harness's other kinds keep the same discipline) and the durability arm still proves the engine: the replacement comes back sealed, is re-unsealed, and re-acquires the HA lock once the dead holder's lease expires -- the marker returns from the database, not a volume. A `backup` block is refused on this engine by the spec, so none rides here.

### The documents

`README.md`: "One mode at a time" becomes "The storage engine and the replica count" (Raft, PostgreSQL by reference, dev; the chart driven from the engine; the disruption budget). `catalog.md`: the opening, the StatefulSet and Service bullets, the cluster prerequisites (a `KubernetesPostgres` on PostgreSQL storage), the key-configuration bullet, the ServiceMonitor and `active_service` sentences, a Common Patterns entry for the new preset. `presets/06-production-postgresql-storage.{yaml,md}` on the catalog's by-reference preset shape, with `maxParallel: 32` and an explainer that says what the engine buys and forfeits; `02-production-ha.md` names `server.replicas`. The e2e headers (`minimal`, `full-surface`, `manifest.yaml`, `profile.yaml`) and the Pulumi project description say engines. The disaster-recovery pattern: dev has nothing to snapshot and a PostgreSQL-stored vault is backed up by its database. The eval bank's q18 answer names `server.raft` and gains a check pinning the guide's sentence. The reference page and the cost estimates regenerate (the estimates gain the new preset's row; the capacity derivation already carried the PostgreSQL exclusion).

### The identity-and-access-platform chart

`openbao_storage` (`string_enum`: `raft` default, `postgresql`). On `postgresql`, the database's `post_init_sql` creates `openbao` under the same `identity` owner as Keycloak's and OpenFGA's databases (the chart's one-owner shape, load-bearing because the operator maintains exactly one credential Secret), and the vault declares the arm exactly as OpenFGA declares its datastore -- host and password by reference to `<env>-identity-db`, `username: identity` -- with `maxParallel: 32` because the database is shared by three consumers and OpenBao's default of 128 per server exceeds a default PostgreSQL's 100 in total. `openbao_disk_size` applies to Raft only. The README's table, diagram, ordering paragraph, and backup note carry both engines, and a day-2 note says the engine is a day-one decision: switching it on a deployed vault does not move data.

## What did not change here

The guide's engine-choice judgment (when to choose PostgreSQL over Raft, and what each means for the bad day) and the skill recipe's teaching follow in their own slice; the console follows the interim catalog release. No live lane ran.

# KubernetesOpenBao's monitor switch should drop OpenBao's own `cluster` label

**Area**: `catalog/kubernetes/kubernetesopenbao` (both engines' rendering of `metrics.service_monitor_enabled`)
**Type**: feature (the field comment and GUIDE now say it; the switch does not do it)

## What a platform engineer sees

OpenBao labels every metric `cluster` with its internal cluster id (`vault-cluster-357a31dc`). The chart's ServiceMonitor keeps it, and a Prometheus adds its external `cluster` label only to series that lack one, so where several Kubernetes clusters report to one monitoring hub, every vault series names a random id instead of the Kubernetes cluster. Seen live 2026-10-04 on three environments: `vault_core_unsealed` at the hub with `cluster=vault-cluster-…` and no way to filter by the Kubernetes cluster.

The workaround, in use since: keep `metrics.enabled`, leave the switch off, and declare a KubernetesServiceMonitor on the active node's Service with `metric_relabelings: [{regex: cluster, action: labeldrop}]`.

## Suggested fix

Have the switch's ServiceMonitor carry that relabeling (the upstream chart's `serverTelemetry.serviceMonitor` takes `metricRelabelings` in recent versions -- verify on the pinned chart), on both engines, with a live proof that a scraped series carries the scraping Prometheus's external `cluster`.

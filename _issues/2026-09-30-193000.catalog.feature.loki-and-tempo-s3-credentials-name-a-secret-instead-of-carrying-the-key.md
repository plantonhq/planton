# Loki's and Tempo's `s3` arms name a Secret instead of carrying the key

**Area**: `KubernetesLoki` and `KubernetesTempo`, the `s3` storage arm's `credentials` (also the `gcs` and `azure` arms' key references)
**Type**: feature (found 2026-09-30 while giving both kinds an `r2` arm; nothing is broken, but the shape costs every composition an extra resource)

## What a platform engineer sees

A platform engineer storing Loki's chunks in an S3-compatible bucket with a static key pair has to declare a separate `KubernetesSecret` holding the pair, point `credentials.access_key_id_secret` and `credentials.secret_access_key_secret` at it by name, and add a `relationships` entry so the Secret is created first. The name fields are plain strings, so the platform cannot order the deploy from them.

## Why

The two arms predate the catalog's secret contract. The newer shape, used by the `r2` arms of `KubernetesLoki`, `KubernetesTempo`, `KubernetesPostgres`, `KubernetesMongodb` and `KubernetesOpenbao`, carries the key pair itself: the access key id as a `StringValueOrRef`, the secret access key as a `sensitive` one the platform resolves from a `$secret/` reference, written by the module into its own Secret. One resource, a real dependency edge, nothing to hand-order.

## Desired behavior

The `s3` arm (and the `gcs` and `azure` key references) accept the key material the way the `r2` arm does. Existing manifests that name a Secret keep working until they move, and the kind's guide says which shape to use.

# The boot contract's glued variable names become underscored

**Area**: operator (`operator/internal/resources/control_plane.go`, the control plane's environment the operator renders)
**Type**: chore -- a naming clean-up with a sequencing rule, no behavior change
**Found**: 2026-09-22 while the platform moved every setting it owns to authored configuration with chosen variable names

## What a person sees

Twelve of the variables the operator sets on the control plane glue words that every other variable separates: `PLANTON_BOOTSTRAP_AUTHORIZATIONMODEL_MANAGE`, `PLANTON_BOOTSTRAP_INFRACHARTS_ENABLED`, `PLANTON_BOOTSTRAP_SECRETBACKEND_TYPE`, `PLANTON_BOOTSTRAP_SECRETBACKEND_AWSSECRETSMANAGER_REGION`, `PLANTON_BOOTSTRAP_TEKTONCONNECTION_ORG`, `PLANTON_BOOTSTRAP_TEKTONCONNECTION_RUNNER`, `PLANTON_CONNECT_METHODAVAILABILITY_HOSTLOGIN_AVAILABILITY`, `PLANTON_CONNECT_METHODAVAILABILITY_OIDC_AVAILABILITY`, `PLANTON_CONNECT_METHODAVAILABILITY_OIDC_REASON`, `PLANTON_CONNECT_METHODAVAILABILITY_PLATFORMAPP_AVAILABILITY`, `PLANTON_CONNECT_METHODAVAILABILITY_PLATFORMAPP_REASON`, `PLANTON_INFRAHUB_IACMODULES_VERSION`. An adopter reading a rendered Deployment, or a `kubectl describe`, meets `SECRETBACKEND` beside `SECRET_ACCESS_KEY` and has to guess which spelling a new variable should follow.

## Why

The glued spelling is Spring Boot's canonical environment form for a property bound straight from the environment (`secret-backend` becomes `SECRETBACKEND`), and it is what a hand wrote the day each was added. It was never required: Spring's legacy environment mapping also accepts the underscored spelling (`SECRET_BACKEND`) for the same property, and the platform's control plane binds these twelve through that relaxed path today, so both spellings bind right now. The platform has since made underscored spelling its rule for everything it owns, with a build guard (`check-config-bound-by-yaml`) whose allow list carries exactly these operator-emitted names until they are renamed.

## What the product should do

1. The operator renders the twelve under underscored names: `PLANTON_BOOTSTRAP_AUTHORIZATION_MODEL_MANAGE`, `PLANTON_BOOTSTRAP_INFRA_CHARTS_ENABLED`, `PLANTON_BOOTSTRAP_SECRET_BACKEND_TYPE`, `PLANTON_BOOTSTRAP_SECRET_BACKEND_AWS_SECRETS_MANAGER_REGION`, `PLANTON_BOOTSTRAP_TEKTON_CONNECTION_ORG`, `PLANTON_BOOTSTRAP_TEKTON_CONNECTION_RUNNER`, `PLANTON_CONNECT_METHOD_AVAILABILITY_HOST_LOGIN_AVAILABILITY`, `PLANTON_CONNECT_METHOD_AVAILABILITY_OIDC_AVAILABILITY`, `PLANTON_CONNECT_METHOD_AVAILABILITY_OIDC_REASON`, `PLANTON_CONNECT_METHOD_AVAILABILITY_PLATFORM_APP_AVAILABILITY`, `PLANTON_CONNECT_METHOD_AVAILABILITY_PLATFORM_APP_REASON`, `PLANTON_INFRA_HUB_IAC_MODULES_VERSION`. Because the platform binds both spellings today, this ships alone, with no platform release paired to it, and every supported platform version keeps booting.
2. Only after the operator release that carries step 1 is the floor for every supported platform does the platform declare the twelve in authored `application-*.yaml` files under the new names (which is when the old spellings stop binding) and remove them from the guard's allow list. The sequence is the whole rule: operator first, platform second, never the reverse.
3. `operator/api/v1/README.md`'s boot-contract table and the platform's `_kustomize` base (which sets four of the twelve for the hosted product) follow the rename in the same changes.

## Recovery until then

None needed: both spellings bind. The names are a reading cost, not a fault.

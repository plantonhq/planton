# Vector Search: Terraform creates a collection's indexes at once, and Google refuses all but one

**Area**: `catalog/gcp/gcpvectorsearchcollection/iac/tf/main.tf` (`google_vector_search_index` with `for_each`).
**Type**: bug.
**Upstream**: hashicorp/terraform-provider-google (draft below).

## What a platform engineer sees

A `GcpVectorSearchCollection` with two or more indexes, deployed on Terraform or OpenTofu, fails its first apply: Google builds one index at a time per collection and refuses a second operation while one runs ("Error 409: unable to queue the operation", measured live 2026-11-21). The first index builds; a second apply creates the next one. The Pulumi module chains its indexes (each depends on the one before), so the same manifest deploys in one go there.

## Why the module cannot simply chain them

The Terraform module declares the indexes as one `google_vector_search_index` resource with `for_each`, and Terraform has no way to order the instances of one resource against each other.

## The behaviour wanted

One apply creates every index, one after another, on both engines.

## The shape chosen

The module keeps `for_each` keyed by `index_id`. A fixed set of chained, `count`-gated index slots was weighed and rejected: removing an index from the middle of the list would shift every later index into the slot before it, and Terraform would destroy and rebuild each of them from the collection's data. Keyed by `index_id`, removing an index destroys that index alone.

The behaviour is taught where a reader meets it: the kind's `GUIDE.md` ("Several indexes on Terraform take several applies"), its `README.md`, the Terraform module's `README.md` and the comment on `google_vector_search_index` in `main.tf`, and the e2e profile. A first Terraform apply of a collection with several indexes creates one; each re-apply creates the next. The Pulumi module chains its indexes and creates them in one apply.

The fix belongs in the provider: `google_vector_search_index` should retry its create while Google refuses it with 409 "unable to queue the operation". Once a provider release carries the retry and the canonical lock picks it up, the kind's `hybrid-two-indexes` scenario proves one-apply creation on Terraform, and the taught caveat leaves the docs.

## Draft upstream issue (hashicorp/terraform-provider-google, not filed)

> **Title:** `google_vector_search_index`: retry create on 409 "unable to queue the operation" while another index operation runs on the collection
>
> **Affected resource:** `google_vector_search_index` (provider 8.7.0)
>
> **Terraform configuration:**
>
> ```hcl
> resource "google_vector_search_collection" "c" {
>   location      = "us-central1"
>   collection_id = "docs"
>   # vector_schema with two vector fields, "dense" and "sparse"
> }
>
> resource "google_vector_search_index" "i" {
>   for_each      = { dense = "dense", sparse = "sparse" }
>   location      = "us-central1"
>   collection_id = google_vector_search_collection.c.collection_id
>   index_id      = each.key
>   index_field   = each.value
> }
> ```
>
> **Expected behavior:** `terraform apply` creates both indexes.
>
> **Actual behavior:** one index is created; the other create fails with `Error creating Index: googleapi: Error 409: unable to queue the operation`. A second `terraform apply` creates it.
>
> **Why:** Vector Search runs one index operation per collection at a time and refuses a second while the first runs. Terraform creates the instances of one `for_each` resource concurrently and cannot order them, and `depends_on` cannot chain instances of the same resource.
>
> **Proposed fix:** add an error retry predicate to the index's create (and its update and delete, which queue on the same collection) that retries a 409 whose message contains "unable to queue the operation", within the resource's create timeout -- the pattern `Is409SyncMutateCannotBeQueuedError` uses for Cloud Scheduler.

## Status

Open. The module half is settled (taught, shape kept); the fix waits on the upstream provider retry.

# Tekton pulls every image from a registry root the install names

**Area**: catalog (`KubernetesTektonOperator`, `KubernetesTekton`)
**Type**: feature -- an install-wide image source for Tekton, the way the platform resource's `spec.imageRegistry` is for Planton's own images
**Found**: 2026-09-24 while routing a GKE cluster's third-party image pulls through a Google Artifact Registry pull-through cache of ghcr.io

## What a person sees

Every image Tekton runs lives on ghcr.io: the operator and its webhook, the Pipelines controller and webhook, and the images every build pod starts with (`entrypoint`, `nop`, `workingdirinit`, the sidecar-logs image). From some cloud regions, pulls from ghcr.io crawl or stall for tens of minutes while the same bytes arrive in seconds from a registry in the same region. A person who mirrors or caches ghcr.io can point the operator at the copy (`operator_image`, `webhook_image`), but nothing reaches the Pipelines images. Those are the ones pulled on every fresh node for every build, so builds stay on the slow path.

Pinning the two operator images by hand has its own trap: the override freezes an exact digest, and the next catalog upgrade that moves the kind's pinned Tekton release runs the new manifests with the old operator image.

## What the product should do

1. The Tekton kinds accept one registry root. When set, every image the install runs, the operator's and each Pipelines component's, the per-build images included, is pulled from `<root>/<path after ghcr.io>`, at the same digest the pinned release names. Empty keeps ghcr.io.
2. The root follows the kind's pinned release: upgrading the catalog moves every image together, with nothing frozen in the manifest.
3. The kind's status or outputs name the images the install is actually pulling, so a person can confirm the mirror is in use without reading the cluster.

## Recovery until then

Leave the images on ghcr.io and wait out slow pulls: a stuck pull completes or can be retried, and a node that has the image keeps it. Don't override `operator_image` or `webhook_image` with a pinned digest unless the next catalog upgrade also updates them by hand.

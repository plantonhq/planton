# CloudflareWorker: a changed schedule fails the apply after Cloudflare has already written it

**Area**: `catalog/cloudflare/cloudflareworker` (OpenTofu: `iac/tf/main.tf`, `cloudflare_workers_cron_trigger.main`; the Pulumi module's cron trigger to be checked the same way)
**Type**: bug (the apply reports failure while the change is live; state and reality diverge)

## What a platform engineer sees

A Worker whose `schedules` change from `["* * * * *"]` to `["0 0 1 1 *"]` is re-applied. The plan is an in-place update of the trigger, the apply writes the new schedule at Cloudflare, and then fails:

```
cloudflare_workers_cron_trigger.main[0]: Modifying... [id=<worker>]
cloudflare_workers_cron_trigger.main[0]: Modifications errored after 1s
[ERROR] Provider produced inconsistent result after apply
  When applying changes to cloudflare_workers_cron_trigger.main[0], provider "registry.opentofu.org/cloudflare/cloudflare" produced an unexpected new value: .schedules[0].created_on: was cty.StringVal("2026-09-30T16:19:58.467126Z"), but now cty.StringVal("2026-10-04T10:24:22.471912Z").
```

The pipeline reads failed, yet the Worker stops running on the old schedule within two minutes: Cloudflare holds the new one. Seen 2026-10-04 on the estate's outside watcher (a stop drill), infra pipeline `infpipe_01m4370p0segq2v5phkqys7mbn` on the desktop instance.

## Why

`schedules` in the provider's v5 resource is a list of objects whose `created_on` and `modified_on` are optional and computed. The module already passes only `cron` (`schedules = [for s in var.spec.schedules : { cron = s }]`), but the provider keeps the prior object's `created_on` in the plan (`[{"created_on": "2026-09-30...", "cron": "0 0 1 1 *"}]`); Cloudflare writes the schedule anew with a new `created_on`, and the provider reports its own result as inconsistent. A provider defect, met through the module.

## What good looks like

A schedule change applies green, and the next plan is empty. Candidates: a provider version that fixes the computed fields (check its changelog first), or replace the trigger on a schedule change (`lifecycle { replace_triggered_by = [terraform_data.<schedules>] }`, keeping the Pulumi module's behaviour equal, which may need `ReplaceOnChanges` on `schedules`). Prove it live: change a test Worker's schedule and back, both applies green, `workersInvocationsScheduled` showing runs on the restored schedule.

## Related

The team's Workers knowledge says an install without `schedules` leaves the old trigger in place, and that a re-created schedule can be listed and not fire for half an hour; both make "change the schedule" the only way to pause and resume, which this bug turns red.

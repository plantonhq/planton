# A secret env variable's literal `value` is not marked sensitive

**Area**: catalog (`catalog/kubernetes/container_env.proto`, `SecretEnvVar.value`; every Kubernetes workload kind that composes `ContainerEnv`)
**Type**: bug -- a secret the schema calls a secret is stored and shown as plaintext
**Found**: 2026-09-18 while teaching the platform to resolve an env variable's bare `valueFrom`

## What a person sees

A developer writes a container secret the way the field comment invites (`env.secrets: - name: DB_PASSWORD / value: "my-password"`) and the manifest is accepted as written. The platform stores the literal in the cloud resource record and in every stack job's cloud-object snapshot, and reads it back in `planton` CLI output, the console's YAML tab, and the run's inputs. Nothing forced the value to be a reference to a managed secret, and nothing masks it afterwards. The same is now true of a `secrets[].valueFrom` the platform resolves: the resolved credential lands in the same `value` slot with the same posture.

## Why

`SecretEnvVar.value` carries no `(dev.planton.shared.options.sensitive) = true`. The option is the one switch the platform reads to force a reference over plaintext and to resolve it just-in-time at deploy, and it "applies to string fields and to the literal value of StringValueOrRef fields" (`shared/options/options.proto`). The `secrets` list is separated from `variables` precisely "to enable appropriate handling (e.g., masking in logs, encryption at rest)" (`container_env.proto`), but the message never told the platform which field to handle. The module side does its part (the literal is written into a Kubernetes Secret, never a plain env var); the platform side has nothing to act on.

## What the product should do

1. `SecretEnvVar.value` carries `(dev.planton.shared.options.sensitive) = true`, so a plaintext literal is refused in favor of a `$secret/` reference and a resolved value is handled like every other sensitive slot. A catalog release carries it; the platform's secret handling picks it up from the descriptor.
2. The `SecretEnvVar` comment stops inviting a plaintext literal ("The value is either provided as a literal ...") and says what the field is for: a reference to a managed secret, or a reference to a Kubernetes Secret key, or a reference to another resource's secret output.
3. The secret-coverage gate reports the field until it does: its name heuristic (`password|token|secret|key|...`) does not match a field spelled `value`, so a per-message rule for `SecretEnvVar` is the way it learns.

## Recovery until then

Write `env.secrets[].value` as a `$secret/<slug>` reference (the runner resolves those on its side), or use `secretRef` onto a Kubernetes Secret the environment already holds. Never a literal.

## Resolution

Fixed in catalog `v0.5.81`. `SecretEnvVar.value` carries `(dev.planton.shared.options.sensitive) = true`, so on Planton a workload's `env.secrets[].value` takes only a `$secret/<slug>` reference: a literal is refused on every write path (create, update, apply, a Service Hub or infra pipeline deploy, and a chart build) with a sentence naming the field and the `planton secret set` command that fixes it. A deploy without the platform still takes the literal.

The field comment no longer invites a literal: it shows the `$secret/` form and says what each source is for. The secret-coverage gate now reads a field's name in the context of its message, so the payload field of a secret entry (a `value` or `data` in a message named `...Secret...`) is held to the marking; the same change marked `Auth0ActionSecret.value` and the `KubernetesSecret` payload (`opaque.data`, `opaque.binary_data`, `tls.tls_key`, `basic_auth.password`, `ssh_auth.ssh_private_key`).

# Fifteen references read a resource's Planton name instead of the Kubernetes object's name

**Area**: catalog foreign keys into `KubernetesSecret`, `KubernetesConfigMap` and `KubernetesServiceAccount`; the reference checker (`pkg/refcheck`)
**Type**: bug (found 2026-09-30 while choosing how a new field should reference a Secret; no published chart wires any of these fields by reference, so nothing is broken in a release today)

## What a platform engineer sees

A platform engineer declares a `KubernetesSecret` named `opensearch-tls` whose `spec.name` is `tls-bundle`, then wires OpenSearch's `security.transport_tls.ca_secret` to it with `valueFrom`. The reference resolves to `opensearch-tls`, the Planton resource's name. No Secret by that name exists in the cluster, and OpenSearch never starts.

## Why

These fields declared `default_kind_field_path = "metadata.name"`. `metadata.name` is the Planton resource's name. `KubernetesSecret`, `KubernetesConfigMap` and `KubernetesServiceAccount` name the object they create with `spec.name`, and publish it as `status.outputs.secret_name`, `configmap_name` and `service_account_name`. The reference checker only proved that a path exists, and `metadata.name` exists on every kind, so the wrong path passed.

The fifteen:
- `KubernetesSecret`: `KubernetesOpenSearch` (7), `KubernetesSolrOperator` (2), `KubernetesSolr`, `KubernetesRabbitMq`, `KubernetesMetricsServer`;
- `KubernetesConfigMap`: `KubernetesGhaRunnerScaleSet`;
- `KubernetesServiceAccount`: the cert-manager issuer's two (`cert_manager_issuer.proto`, shared by `KubernetesIssuer` and `KubernetesClusterIssuer`).

The references into `KubernetesClusterIssuer` by `metadata.name` are sound: that kind has no `spec.name`.

## Resolution

Fixed in `v0.5.102`:
- each of the fifteen points at the target's published name output, which also resolves only once the object exists;
- `pkg/refcheck` refuses a `metadata.name` path into a kind whose spec declares its own `name` (`ownNameReason`, pinned by `TestOwnNameReason`). `TestForeignKeyReferencesAllResolve` reported all fifteen before the fix and passes after it;
- the reference pages and `catalog/_docs/reference-graph.yaml` are regenerated;
- the kind update rule says which name a reference points at.

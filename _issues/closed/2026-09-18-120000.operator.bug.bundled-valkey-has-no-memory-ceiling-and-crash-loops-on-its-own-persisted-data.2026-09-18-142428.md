# The operator's bundled Valkey has no memory ceiling and crash-loops reloading its own persisted data

**Area**: operator (`operator/internal/resources/valkey_helm.go`; `KubernetesPlantonPlatform.spec.redis`)
**Type**: bug -- an unrecoverable outage every self-hosted install can reach by running long enough
**Found**: 2026-09-18 on a self-hosted instance at `v0.0.72`, 37 hours after a fresh install

## What a person sees

The console loads its shell and then renders skeletons forever; the CLI hangs on any read. The front door keeps returning 200, so an uptime check says nothing is wrong. In the cluster, the platform's Valkey pod (`<platform>-redis-primary-0`) is in `CrashLoopBackOff` with every termination `OOMKilled`, and the control plane logs `RedisCommandTimeoutException: Command timed out after 1 minute(s)` on every request that touches the cache.

## Why

The operator renders the Bitnami Valkey chart with no `resources`, no `resourcesPreset`, and no `commonConfiguration`, and with `persistence.enabled: true`. So the pod gets the chart's smallest preset (a 192 MiB memory limit), Valkey's defaults (`maxmemory 0`, `noeviction`), and append-only persistence. The dataset grows until the kernel kills the pod; because every write was persisted, each restart reloads more data than the pod may hold and is killed again before it serves. The loop cannot end on its own. On the instance where it was met, the dataset had reached 158 MiB in 37 hours.

`spec.redis` exposes only `storage_size` and `storage_class_name`, so no manifest can change any of this. The catalog's own `KubernetesValkey` kind carries every knob (`config.max_memory`, `config.max_memory_policy`, `config.append_only`, `config.snapshots_disabled`, `resources`) and its field comment says "always set this for caches"; the operator's Valkey is the one Planton cache that does not follow it.

## What the product should do

1. **Sane defaults for the bundled cache, with no field required**: a memory limit the operator chooses (1 GiB is right for what the control plane stores), `maxmemory` beneath it (768 MiB) with `allkeys-lru`, and no persistence -- this store is a cache and coordination store; a restart is a cold cache, never a loss.
2. **`spec.redis` grows `resources`, `max_memory`, `max_memory_policy`, and `persistence`** so an install can size or re-enable what it needs, in the same words the `KubernetesValkey` kind uses.
3. **The same review for every other workload the operator renders** (PostgreSQL, Temporal, OpenFGA, the identity server, OpenBao, the control plane, the console, the runner): each with a limit the operator chose and a reason beside it, never a chart's smallest preset by omission.

## Recovery until then

Scale the Valkey StatefulSet to zero, delete `appendonlydir` from its volume with a one-shot pod, scale back. About one minute; the cache starts empty under the same limit.

## Resolution

Fixed in `operator/v0.20.0` (changelog `_changelog/2026-09/2026-09-18-150000-the-operator-sizes-every-workload-it-renders-the-bundled-store-gets-a-ceiling.md`). The store runs with a 768mb dataset ceiling and `allkeys-lru` eviction under a 1Gi memory limit (requests 100m/256Mi), the chart's preset named off, and `spec.database.redis` gained `persistence`, `maxMemory`, `maxMemoryPolicy`, and `resources` in the `KubernetesValkey` kind's words. Every other workload the operator renders now carries a sizing the operator chose, as named constants with the reason beside them.

One line of the fix shape above was wrong and is corrected here: **persistence stays on by default.** The operator wires both the cache and the Tekton log stream (`REDIS_CLUSTER_*` and `TEKTON_LOGS_REDIS_*`) at this one store, so it holds every live build-log stream until the run archives it to the pipeline-logs bucket; a restart with no volume blanks the log a person is tailing mid-build. The hosted product already persists exactly that store for exactly that reason. The crash loop was unbounded growth reloading into a preset-sized limit, not persistence itself; the ceiling is the fix, and what is persisted always fits under it.

# Firebase kinds for the GCP catalog, so a Planton environment's mobile push is declared, not clicked

**Area**: catalog, provider `gcp` (new kinds beside `GcpProject`, `GcpServiceAccount`, `GcpProjectIamMember`)
**Type**: feature (a gap found 2026-09-17 while listing what the hosted product's dev environment needs; the founder's direction is to fold Firebase into the GCP catalog rather than mint it in the console)

## What the product needs from Firebase

One thing: Firebase Cloud Messaging for mobile push. The control plane's notification domain initializes the Firebase Admin SDK in one of three modes -- an explicit service-account key JSON, opt-in Application Default Credentials (GKE Workload Identity's metadata server, the keyless posture), or disabled -- and push is advisory, so a credential problem never fails boot. The mobile app (`ai.planton.mobile` on Android and iOS) needs a Firebase app registration per platform to receive tokens, and iOS additionally needs an APNs authentication key uploaded to Firebase.

## What the catalog has and lacks

Has: `GcpServiceAccount`, `GcpServiceAccountIamMember` (Workload Identity binding), `GcpProjectIamMember` -- enough for the keyless identity (`roles/firebasemessaging.admin` on a service account bound to the control plane's Kubernetes ServiceAccount).

Lacks, all of it reachable through Google's Firebase Management API (unlike OAuth clients, for which Google exposes no API):

1. **`GcpFirebaseProject`** -- enables Firebase on an existing GCP project (`projects.addFirebase`; idempotent, one per project) and enables the `firebase.googleapis.com` and `fcm.googleapis.com` services. Outputs: the Firebase project id, the default GCP resources Firebase creates.
2. **`GcpFirebaseAndroidApp`** -- registers an Android app (`projects.androidApps.create`: package name, display name, optional SHA certificates) and exposes its client configuration (`androidApps.getConfig`, the `google-services.json` content) as an output the mobile build reads.
3. **`GcpFirebaseIosApp`** -- registers an iOS app (`projects.iosApps.create`: bundle id, display name, optional App Store id / team id) and exposes `GoogleService-Info.plist` as an output.
4. Possibly **`GcpProjectService`** (service usage: enable an API on a project) if the kinds above should not each enable their own APIs -- the catalog has no general API-enablement kind today.

Stays a console step, and belongs in the Google vendor record's seven lifecycle facts: the **APNs authentication key** upload for iOS (Apple mints it; Firebase's API has no method to upload it).

## One decision the kinds force into the open

Firebase is enabled per GCP project, and Planton's estate runs one GCP project for everything (the standing directive). So one Firebase project serves dev, demo, and prod; environments separate by the service account each control plane runs as (`roles/firebasemessaging.admin` bound to that environment's control plane only) and by the control plane the mobile app is signed in to, not by Firebase project. The mobile app registers once per platform (`ai.planton.mobile`), and its tokens are valid for whichever environment's control plane the person uses. The environment chart declares the identity per environment; `GcpFirebaseProject` and the two app registrations are declared once, in the environment that owns the estate's shared Google resources.

## Expected

The three kinds above (and the service-usage kind if chosen) with both engines, `permissions.yaml`, e2e scenarios, and a guide that teaches the keyless posture: no key JSON, the control plane's identity bound to a Firebase-messaging role, the app configurations as outputs the mobile build consumes.

# ABANDON deletes the env secrets an abandoned workload runs on

**Area**: `catalog/gcp/gcpvertexaiagentengine`, `catalog/gcp/gcpcloudrun`, `catalog/gcp/gcpcloudrunworkerpool`; the Terraform modules' `iac/tf/secrets.tf` and the shared Pulumi helper `pkg/iac/pulumi/pulumimodule/provider/gcp/envsecrets`.
**Type**: bug.

## What a platform engineer sees

A Vertex AI Agent Engine agent, a Cloud Run service, or a Cloud Run worker pool whose environment carries a stored secret (`secretEnv[].value` on the agent, `env[].secretValue` on the service and the pool) is destroyed under `deletionPolicy: ABANDON`. The workload stays running, as ABANDON promises. The secrets it reads do not: the destroy deletes the Secret Manager secret the module created for each variable, its version, and the runtime identity's `roles/secretmanager.secretAccessor` grant on it. The workload keeps serving from instances that already read their secrets, and its next instance start fails because the version it names is gone.

## What each engine does today

- **Terraform / OpenTofu.** `secrets.tf` declares `google_secret_manager_secret`, `google_secret_manager_secret_version`, and `google_secret_manager_secret_iam_member` per variable, none of them tied to `spec.deletion_policy`. The workload resource depends on them, so a destroy removes the workload first (a no-op under ABANDON), then the grant, the version, and the secret, each with its provider's default delete.
- **Pulumi.** `envsecrets.Store` creates the same three resources with no deletion option drawn from the spec, so `pulumi destroy` deletes them the same way after the abandoned workload leaves state.

## Why the module cannot simply abandon all three

The secret and the version carry a client-side `deletion_policy` in Google's provider (`ABANDON` is accepted on both), so they could follow the workload's policy. The grant cannot: `google_secret_manager_secret_iam_member` is one of the provider's generic IAM resources and has no `deletion_policy`, so a destroy always removes the member. Keeping the secret and its version while the grant goes still leaves the workload unable to read them. Pulumi's `RetainOnDelete` resource option could keep all three on that engine, but Terraform has no equivalent short of removing the resources from state by hand, so the two engines would diverge.

## What the catalog says now

Each kind's `deletion_policy` comment, its stored-secret field comment, and its GUIDE state the behaviour above and point a workload meant to outlive its manifest at a secret the person owns (`secretRef` on the agent, `valueFromSecret` on the service and the pool).

## The behaviour wanted

Under ABANDON the workload keeps everything it needs to start again: the stored secrets, their versions, and the identity's access to them stay in Google Cloud, unmanaged, alongside the workload. Under DELETE and PREVENT nothing changes. One design both engines can express: carry the policy to the secret and version (`deletion_policy = "ABANDON"` / `RetainOnDelete`), and replace the per-secret IAM member with a grant that survives the destroy -- for example one written as part of the secret's own resource where the provider allows it, or a grant both engines abandon by the same mechanism. Whatever the shape, the spec comments drop the warning once both engines keep the secrets.

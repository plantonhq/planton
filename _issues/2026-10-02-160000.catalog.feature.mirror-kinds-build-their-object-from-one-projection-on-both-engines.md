# Every Kubernetes mirror kind builds its object from one projection on both engines

**Area**: the Kubernetes manifest projection kinds (registry `kubernetes_manifest_projection`): their Pulumi modules, and three Terraform modules the generator cannot yet express
**Type**: feature (convergence), with one defect it removes

## What a platform engineer sees today

**The engines label the same object differently.** Deploy an Istio AuthorizationPolicy with OpenTofu and its object carries `planton.ai/resource`, `planton.ai/resource-name`, `planton.ai/resource-kind` and the other identity labels. Deploy the same manifest with Pulumi and it carries `app.kubernetes.io/name`, `instance`, `managed-by` and `component` instead. Anyone selecting a kind's objects by Planton's labels misses the ones Pulumi created. The generated Terraform module's own comment claims the two label sets are identical.

Fifteen Pulumi modules stamp the `app.kubernetes.io/*` set (`grep -l app.kubernetes.io/managed-by catalog/kubernetes/*/iac/pulumi/module/locals.go`). Found by reading both engines; not yet observed on a live object.

**The Pulumi side maps every field by hand.** Each mirror kind's Pulumi module copies the spec into a typed crd2pulumi struct field by field (AuthorizationPolicy's is about 240 lines), while its Terraform module is generated and passes the spec through verbatim. A field the spec gains reaches the object through Terraform and silently not through Pulumi until someone extends the hand mapping.

## What exists now

- `pkg/kubernetes/manifestprojection` renders a projection kind's manifest into its object: the spec under the custom resource's own keys, the namespace reference and any `kubernetes_object_metadata` fields routed to metadata, and the identity labels (one definition, also read by the Terraform generator).
- `pkg/iac/pulumi/pulumimodule/provider/kubernetes/manifestcr` applies that object. `KubernetesPrometheusRule` is the first module on it; its Pulumi module is about 40 lines and its live e2e proves both engines produce the declared object exactly.
- `TestManifestModuleDrift` holds every projection kind's Terraform module to the generator. It names three it cannot yet express in `manifestModuleGaps`:
  - `KubernetesHttpRoute`: its `first_host` output.
  - `KubernetesListenerSet`: an output that is the parent Gateway's name.
  - `KubernetesKarpenterNodePool`: locals that default and reshape fields, so its spec is not a pure projection.

## Desired behavior

- Every projection kind's Pulumi module applies its object through `manifestcr.Apply`. The two engines then label and shape the object identically by construction, and a new spec field needs no module change.
- Each of the three named gaps is resolved one of two ways: the generator learns the output (a mapping rule, proven on both engines), or the kind stops claiming `kubernetes_manifest_projection` because its spec abstracts over the custom resource. Either way its entry leaves `manifestModuleGaps`.
- Each migrated kind's e2e lanes run live on both engines after the move.

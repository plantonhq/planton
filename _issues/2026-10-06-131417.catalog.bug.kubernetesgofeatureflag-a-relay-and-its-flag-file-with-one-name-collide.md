# KubernetesGoFeatureFlag: a relay and its flag file with the same name collide on one ConfigMap

**Area**: `catalog/kubernetes/kubernetesgofeatureflag` and `catalog/kubernetes/kubernetesgofeatureflagflagfile` (both IaC modules)
**Type**: bug (an install fails, or the two resources fight over one object, for a natural naming choice)

## What a platform engineer sees

They declare a relay and its flag file in one namespace and give both the obvious name, `flags` (or `feature-flags`). The relay's `relay-proxy` chart creates a ConfigMap named after the relay (`fullnameOverride` pins it to `metadata.name`, `locals.go`), which holds the relay's own configuration. The flag file renders its ConfigMap named after the flag file (`module/main.go`, `NewConfigMap(locals.Name)`), which holds the flags. With one name, the second install meets an object it does not own: an "already exists" refusal, or Helm refusing to adopt an object without its ownership labels. Nothing in either kind's validation, docs or presets warns about it. The catalog's own e2e fixtures happen to use two names (`e2e-goff-min`, `e2e-goff-flags`).

Found while planning Planton's own estate (the relay `feature-flags` with its flag file). The estate avoids it by naming the file `release-flags`.

## What good looks like

The collision cannot be written. Options, in order of preference:
1. The relay's chart ConfigMap takes a suffix (`<name>-config`). This is a module change, so check whether `fullnameOverride` lets the chart's ConfigMap name diverge, or render the configuration ConfigMap ourselves.
2. A cross-resource check is not available to one kind's validation, so at minimum both `catalog.md` pages and the `KubernetesGoFeatureFlagFlagFile` spec's namespace comment say "give the relay and its flag file different names", and the flag-file preset uses a name that cannot equal the relay preset's.

Prove it live: a relay and a flag file named alike install green (option 1), or the docs carry the warning (option 2).

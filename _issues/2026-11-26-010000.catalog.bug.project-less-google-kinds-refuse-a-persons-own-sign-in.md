# Google kinds that live above a project refuse a person's own gcloud sign-in

**Area**: the GCP kinds whose `iac/permissions.yaml` declares `caller_project_services`: `gcpcloudidentitygroup`, `gcphierarchicalfirewallpolicy`, `gcpkmsautokeyconfig`, `gcploggingsink`, `gcpmodelarmorfloorsetting`, `gcporgpolicy`, `gcporgpolicycustomconstraint`, `gcpsccbigqueryexport`, `gcpsccmuteconfig`, `gcpsccnotificationconfig`.
**Type**: bug.

## What is broken

These kinds call APIs that bill each call's quota to the caller's own project, and their resources name no project the call can borrow. A service account or keyless identity has a project of its own, so the lanes pass. A connection that signs in as a person (runner mode on a gcloud configuration, or a local run under `gcloud auth application-default login`) has none, and Google refuses with 403 "requires a quota project, which is not set by default". Whether a run passes then depends on whether the person's credentials file happens to carry a `quota_project_id`.

`GcpBillingBudget` had the same defect and is fixed: its spec carries `quota_project_id` (a `GcpProject` reference, `containment_exempt`), its OpenTofu provider sets `user_project_override` and `billing_project` from it only when set, its Pulumi module calls `pulumigoogleprovider.GetWithQuotaProject` only when set, and its permissions manifest asks for `serviceusage.services.use` on that project behind the field's condition. Proven on both engines under a person's sign-in (the released module reproduced the 403 first).

## What is asked

Give each kind above the same field and wiring, prove each under a person's credential, and say in each kind's docs which project carries the quota. Where a kind's spec already names a project its calls could bill (none of the listed ones does today), use that instead of a new field.

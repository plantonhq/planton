# Deploy, Promote, Rollback, and Redeploy — The Delivery Verbs

A service's version reaches an environment two ways: a push builds it and deploys it, or someone delivers a version that already exists. This file is about the second way — the four verbs that deploy without a build of their own — plus the two build-and-deliver shapes people ask for by name: releasing by tag, and trying a branch in one environment.

Read this when someone wants a version that runs in one environment to run in another, when something is wrong in an environment and the previous version should come back, when someone has an image built elsewhere (their CI, their laptop) and wants it running, when someone wants a tag push to BE the release or a feature branch running in dev, when a deployment you started refuses and you need to explain why in terms the person can act on, when a resource read Unchanged and the person wants it applied anyway, when someone asks whether the cloud still matches what a service runs, when a direct change to one of a service's resources was refused, when a resource left the service's configuration and the person asks what happens to it, when a run waits on a removal question, or when someone wants to know what a promotion, rollback, redeploy or deploy would do before it runs.

## Releasing by tag, and trying a branch

**Tag releases**: with `build.triggers.tags.deploy: true` on the service (optionally narrowed by `tags.patterns` like `["v*"]`), a matching tag push builds and rides the FULL walk along the service's Promotion Paths — gates, protection, and approvals exactly as a default-branch push. A tag is a release; without the flag, tag pushes build only, and the run says so. The platform's Dockerfile and Buildpacks builders push a tag build's image under its commit sha AND under the tag (`v1.4.0`) on the same digest, and the run records it as the artifact's `release_tag` (`planton follow` prints "Also tagged v1.4.0"). A git tag no image tag can carry (image tags are letters, digits, `_`, `.` and `-`, up to 128 — `release/1.4` is not one) is pushed under its commit only, and the build log says so in one sentence; that is expected, not a failure. A custom pipeline tags its image however it chooses.

**Releasing a tag by hand** (`planton service run <service> --tag <tag>`; the `tag` parameter of `run_service_pipeline`; **Release a Tag** in the console's Run dialog): a tag release exactly as if the tag had just been pushed — the tagged commit builds and walks every environment. Use it to re-release a tag whose push was missed, or to ship an existing tag without pushing a new one. `--tag` stands alone (never with `--branch` or `--commit`), and the platform refuses it when the service's tag triggers are off or the tag matches none of its patterns; a tag the repository does not have is refused naming the tag and the repository. Relay those sentences as written.

**Services with no trigger branch**: `build.triggers.disableTriggerBranches: true` means no branch starts the promotion walk, and an empty `build.triggers.branches` no longer falls back to the default branch. Tags still release, and every branch in `deploy.branchDeployments` still builds and deploys into its one environment; a push to any other branch is skipped ("no branch starts this service's promotion walk … and branch 'X' is not mapped to an environment"). This is the right shape for a service that ships on `v*` tags, or one promoted by merging between mapped branches (`dev`, `staging`, `release`); never name a branch that is never pushed to keep the default branch from building, and never write `branches: []` for that — an empty list means the default branch. It is refused only beside listed `build.triggers.branches`, so remove them in the same change; branch mappings stay. A manual run of such a service must name what to build: a bare run is refused with "service '<slug>' has no trigger branch to build by default, so name what to run: planton service run <slug> --tag <tag> (or --branch <branch>)" — run the tag, or a mapped branch (it deploys to its environment), or another branch with `--deploy-env`. Such a service has no promotion walk — only a tag release walks its environments — so a run by `--commit <sha>` must say where it deploys: `--branch <mapped branch>` or `--deploy-env <env>`; alone it is refused with "service '<slug>' has no promotion walk, so a run by commit deploys only where you name: add --deploy-env <env>, or --branch <branch> to deploy where that branch is mapped (dev → dev, …)".

**Branch deploys** (`planton service run <service> --branch <branch> --deploy-env <env>`): builds the branch's head and deploys it into exactly ONE environment — no promotion walk. A branch outside the service's trigger branches NEVER walks the Promotion Paths: without `--deploy-env` it builds and stops, with the reason on the run ("name a deploy environment"). This is the try-my-feature-branch-in-dev shape. An explicit `--commit <sha>` is different: its branch label is empty unless `--branch` states the claim (the record never claims a branch it cannot prove). Unlabeled, it is the deliberate release act and keeps the full walk — on a service whose trigger branches start one; labeled with a mapped branch, it deploys where that branch is mapped.

**Standing branch-to-environment mappings** (`deploy.branchDeployments` on the service): for teams whose branches ARE their environments — `develop` deploys dev, `release` deploys staging — a mapping makes every PUSH to that branch deploy into exactly its one environment, no manual run needed, and a manual run of the branch (`--branch develop`, or the console's Run dialog) deploys there too, exactly as its push would; `--deploy-env` wins over the mapping. If the mapped environment's stage later becomes Promotion Only on its path, the mapping is dead: the branch's runs build and deploy nothing, and the run names the ways out (promote a deployment into it, remove the mapping — until then the service's settings can't be saved — or let pushes reach it on its Promotion Path). Gates, protection, and approvals apply exactly as anywhere else; promotion on this topology happens by MERGING between branches. A branch can be a trigger branch (the full walk) or a mapped branch (one environment), never both — the save refuses the ambiguity. For git-maintained services the mapping is also the record sync's authority: the mapped branch's pushes keep its environment's configuration entry current from its OWN tree, so an overlay that exists only on the dev branch still shows on the record, marked for dev with its branch and commit named.

## What the verbs actually do

**Deploy** (`planton service deploy <service> --env <env> --image <ref>`) takes a container image built ANYWHERE and deploys it into one environment, rendering the manifests from the service's current declared configuration (the record's `deploy.environments` — manually authored or git-synced alike) with the image injected. Optional `--commit`/`--branch` carry the image's provenance so the run's history reads honestly. This is the terminal twin of the external-CI deploy step; with `--follow` it exits non-zero unless the deployment verifiably succeeded (a failed run OR a failed rollout verdict fails the command — an honestly unverifiable one does not).

**Deploy from the working tree** (`planton service deploy <service> --env <env> --image <ref> --from-tree`, run from the repository's project root) is the same verb with the configuration taken from the folder the person is standing in instead of the record: the environment's `_kustomize/overlays/<env>` renders on their machine (the same renderer `service env` uses) and travels with the deploy; the control plane injects the image, the pull login, and the serving hostname exactly as for a synced entry, writes the render onto the record's entry for that ONE environment — stamped with who rendered it, at which commit, and whether the tree carried uncommitted changes — and then runs the deploy through the same gates, verification, URLs, and receipt. Recommend it when a git-maintained service has never been pushed through the build lane (the record's environments are empty, so a plain deploy refuses), or when someone is shaping an overlay and wants to see it run before committing. What to know when recommending it: it accepts only git-maintained services (`deploy.kustomize`; a manually-declared service deploys the record without the flag, or ejects first); it is for a person at a terminal, never a CI workflow (an external-CI credential is refused — the platform cannot verify which branch a checkout came from); the run is named "Deploy … from the working tree" and the receipt carries the tree's provenance; and git stays the stronger writer — the next push to the branch that drives the environment with the same content takes the entry back for git and redeploys nothing, so the record stops saying "working tree" the moment the tree agrees. The CLI prints one line before sending — the overlay, how many manifests, the commit and branch, and whether there are uncommitted changes under the kustomize directory — read it back to the person; "uncommitted changes" means the render is something no commit can reproduce yet.

**Promote** takes the artifact from an existing deployment and deploys it into another environment, together with the configuration that was captured alongside that artifact. It does not rebuild, and it does not read the service's current configuration. What ran in staging is what runs in production — the same image, the same settings, verified together. A resource production runs for the service that the promoted configuration no longer has is removed (see What a run removes).

**Rollback** puts an environment's previous deployment back by re-applying that deployment's own artifact and configuration exactly as they ran. With no target named it restores the immediately preceding deployment, so rolling back twice returns to where you started. Naming a specific past deployment restores exactly that one, and what the service added after it is removed: a rollback to Run #128 destroys a resource Run #130 introduced. Rollback never targets what runs now; naming the current deployment is refused with the verb that does it: "Run #128 is what runs in prod now. Redeploy it instead: planton service redeploy checkout-api --env prod."

**Redeploy** (`planton service redeploy <service> --env <env> [--reapply-all]`; `redeploy_service`; **Redeploy** on the environment in the console's Deployments tab, or on a drifted environment's callout) applies the environment's CURRENT deployment again — its own artifact and configuration, exactly as they run. Every resource that still matches what was last applied is skipped, and every resource a drift check found changed outside Planton runs, so a redeploy is how drift is put back. It also finishes the removals an earlier run left (a failed destroy, or one left in place whose reason is gone). A protected environment still stops at its gate. It refuses an environment with nothing deployed, a pull request's preview, and a deployment observed from GitOps or missing its artifact or configuration. Use it when the version is right and the cloud has moved; use rollback when the version is wrong.

All four answer with a **run**, not a deployment record. A deployment takes time, can pause for an approval, and can fail — so what comes back is something to follow. The deployment record appears when the environment succeeds. The answer carries the run's id AND its number within the service (`run_number`): the CLI prints "promotion to staging started — Run #129" and the follow hint `planton service follow checkout-api 129`. Say the number to the person; it is the handle every surface shows.

**Promote** and **Rollback** in the console have one home each. Promote lives on the step between two environments, wherever an environment chain is drawn: the Delivery Path on the service's Overview, and the strip of a build run's page. Roll Back lives in the Deployments tab, beside the history it restores from (each environment offers Roll Back; a past deployment offers Roll Back to This), and Redeploy and Check for Drift sit beside it on each environment. The Promote confirm asks exactly what will happen ("Promote 'Fix login' to staging?"), names the source ("From dev · Built by Run #128"), offers **Re-apply Every Resource**, and warns in one line when the move is unusual: the target is ahead of or diverged from the source, was just rolled back, or the source failed its checks. Promoting from a build run's page keeps the person on that page: the environment's panel becomes the promotion, live, with the promotion run one door away. When a person would rather click than type — or wants to SEE what a rollback restores before committing to it — pointing them there is a complete answer.

Deploy differs from promote in what configuration ships: deploy renders the service's CURRENT declaration (today's configuration, the named image); promote re-applies the CAPTURED configuration (the tested pair). When a version already runs in another environment, promote is the right verb; deploy is for versions Planton has never deployed.

## Why they are exact, and why that matters when explaining them

Every run captures the resolved manifests for each environment it planned, and every deployment record additionally carries the manifests it applied. Those captures are what make these verbs trustworthy: the platform is re-applying bytes that already ran rather than re-deriving them. Practical consequences worth stating to a person:

- A rollback during an incident restores a state that genuinely existed. It cannot produce old code paired with configuration someone changed last week.
- Neither verb needs the repository to be reachable or a build system to be healthy.
- A promotion moves a tested pair. If the configuration for the target environment changed after the artifact was built, promotion still deploys the tested configuration — that is the promise, not a limitation to apologize for.

If someone wants the same version with *current* configuration, that is a different intent. Say so plainly: the honest path today is a new build (for services whose configuration lives in git, a configuration change IS a commit, so pushing is the natural route).

## Only what moved runs, and `--reapply-all`

Every deploy — a push's, and deploy, promote, rollback and redeploy alike — applies only the resources whose inputs moved since their last successful deploy. Before a resource runs, the platform compares what it would deploy with what its last successful deploy applied: its settings, the values it reads from other resources, its secrets' current versions and its variables, the account it deploys into, the module version, and whether anything it sits on was rebuilt. An exact match runs no job. The resource reads **Unchanged since Run #126**, naming the run whose job last applied it ("Unchanged since r11" when a stack's run applied it last), and hands that job's outputs to everything that depends on it. The CLI adds the job's id ("Run #126 (ij_…)"), because the job is where its logs live. Any doubt runs the job, so a resource whose module follows a branch, whose secret version cannot be read, or whose connection signs in through the runner's own machine or a broker always runs. A resource whose lifecycle events are disabled (`planton.dev/infra-job.disable-on-lifecycle-events: "true"`) reads **Unmanaged**: it is left alone, and no job ever runs for it.

What this means when you explain a delivery:

- **The deployment record lists every resource with what happened to it**: applied by this deploy's job, unchanged (with the run and job that last applied it), or unmanaged (no job). The rollout's resources check counts them honestly, for example "2 applied; 3 unchanged since their last deploy; 1 unmanaged and left alone", or "every resource in the environment is unchanged since its last deploy". Unchanged is a success, not a skip: never report it as something that failed to happen.
- **A delivery runs only what differs from what the environment already runs.** Each resource is compared with that environment's own last deploy of it. When the captured configuration matches what the target ran before and only the image moved, only the resources that carry the image run; the rest read unchanged.
- **Logs follow the job that did the work.** `planton service logs` on an unchanged resource says it is unchanged since the run that last applied it ("Run #126 (ij_…)"), that this run started no job for it, and follows that job; an unmanaged resource has no engine logs.
- **A change made outside Planton is invisible to the comparison until a drift check finds it.** Someone edited the resource in the cloud console, or deleted it: nothing Planton deploys moved, so a plain delivery reads it unchanged. Check for drift first (next section): a drifted resource is no longer unchanged, so a plain redeploy puts it back. To apply every resource regardless: `--reapply-all` on `planton service deploy`, `promote`, `rollback` and `redeploy`; `reapply_all` on `deploy_service`, `promote_service_deployment`, `rollback_service_deployment` and `redeploy_service`; **Re-apply Every Resource** in the console's Promote, Roll Back and Redeploy dialogs. Every resource then runs its job; an unmanaged resource stays Unmanaged either way. A delivery run is never rerun (below), so applying everything again means asking the verb again with the flag. With no backend configured, the deploy already applies every resource in the tree, so the flag is refused there.

## Changed outside Planton: check for drift, then Redeploy

```
planton service drift check <service> --env <env>   # checks every resource the environment's current deployment holds
planton service drift show <service> --env <env>    # what the latest check found, without checking again
planton service redeploy <service> --env <env>      # puts the drifted resources back
```

A service environment's drift check compares, for every resource of its current deployment that Planton deployed, what Planton last applied with what is really in the cloud, setting by setting, and writes nothing. It never waits for approval, so run it freely; it needs the same right as a redeploy (deploy on the service in that environment). The CLI follows until every resource has its verdict: In Sync, Drifted (each change with the value Planton applied and the value in the cloud now; a secret only as "Hidden value changed"; a resource deleted by hand as "Deleted Outside Planton"), or Couldn't Check with its reason. Exit codes match the stack's drift verbs: `0` checked, `1` a resource could not be checked, `2` the check could not run; `--detailed-exitcode` adds `4` for drift found. Agents use `check_service_drift` and `get_service_drift`. Asking again while a check runs answers with the running check. The check is refused, in these words, when there is nothing to compare: "Nothing is deployed to prod yet, so there is nothing to check." and, for a deployment observed from GitOps, "Planton deployed nothing that runs in prod, so there is nothing to compare the cloud with."

The service page shows the result on each environment ("In Sync", "Drifted · 2 resources", "Checking 3 of 7…", "Couldn't Check"), and the person who checked is notified when something drifted or couldn't be checked. Putting it back is Redeploy; keeping the cloud's change on purpose means carrying the value into the service's configuration and deploying. Which one is the person's call: say what drifted, and offer both.

## A service's resources change only through the service

Every resource a service deploys names the service as its owner. While the service is live and its latest run into that environment planned the resource (whether that run succeeded or not), a direct deploy, destroy, purge, rename or configuration edit of the resource is refused, naming the service and the way through:

```text
AwsRdsInstance 'orders-db' in 'prod' is owned by service 'checkout-api', so it changes only through that service: change its configuration and deploy, or redeploy it (planton service redeploy checkout-api --env prod). Refreshing it and repairing its state stay available here.
```

The rule exists because the service's next deploy would silently undo a direct change. Relay the refusal and offer the service's path; never work around it. Checking the resource for drift stays allowed. Once a run into the environment no longer plans the resource (it was removed from the service's configuration), the guard frees it, and the run removes it (next section).

## What a run removes

A service's declaration is what runs in its cloud. A resource the service owns in an environment and a run no longer declares — renamed or deleted in the kustomize tree or the Configuration tab, or missing from the configuration a promotion or rollback carries — is a **removal** of that run. The run lists its removals from the moment it exists and carries out each one at the very end, after everything declared applied, the rollout verified, and the deployment record was written:

- **Destroyed** — the default, a database included. It is the service's own change, made with the service's authority exactly like its applies, so a developer's push destroys it.
- **Kept in AWS** (the provider's own name) — a resource marked `planton.dev/keep-on-provider: "true"` (an annotation under the resource manifest's `metadata.annotations`, in each environment's configuration that should keep it) is never destroyed: the service lets go of its record and it keeps running, findable and adoptable. An Unmanaged resource is always kept the same way, and a protected gate's approver can also choose Keep (below).
- **Left in Place** — something stops the destroy: `planton.dev/prevent-destroy`, the resource's own deletion protection, something else still reading it (another stack or service, a resource deployed on its own, or what this service still declares), or a kept resource living inside it. The row says why and names the way out. The resource stays the service's, `listResources` keeps listing it under no-longer-declared, and the next run tries again once the reason is gone.

What to know when explaining a removal:

- **A failed apply or a failed verification removes nothing.** Removals read "Not run: nothing is removed while what the service declares did not all apply".
- **A removal never fails a deployment.** A destroy that fails leaves the environment deployed with "1 removal failed", promotion carries on, and the next run (or a redeploy) tries again. A cancel or a newer push taking over during the removals leaves the environment deployed too ("Removals not run: the run was cancelled").
- **In an unprotected environment nothing asks.** A push, `planton service run` (`run_service_pipeline`) and a deploy from the service's own CI are the declaration itself: each destroys every removal, a database too, unasked. A renamed database is a removal, so before a push that renames or drops a resource, read the environment's drift (`get_service_drift`, its `no_longer_declared`) and say what goes; mark a resource keep-on-provider to keep it running.
- **The other delivery verbs say what goes first.** Promote, rollback, redeploy and any other deploy read their dry run: at a terminal they name each removal and ask; `--yes` starts them without a terminal and they print what they removed; with neither they refuse and print the same command with `--yes` added. Into a protected environment they say the approver decides those removals at the gate, and ask nothing more. Agents (`deploy_service`, `promote_service_deployment`, `rollback_service_deployment`, `redeploy_service`) pass `confirm` when the run destroys something: once the person agreed, or under their word to carry on without asking (for this task), and then say exactly what was destroyed.
- **In a protected environment, the approver decides every removal.** The gate lists each one, and approving decides them all: each is destroyed unless the approver keeps it. The approval covers exactly the records shown: a removal that appears after it, or whose resource was replaced since, asks on its own row.
- **Who answers.** Whoever may decide the run's gates: approve rights on the environment, and in a protected one not the person who started the run while another approver exists. The person who started the run is told why it waits. You answer one only on the person's word — the decision they stated, or their word to carry on without asking (for this task), after which you say exactly what was destroyed — and never on a run your own person started: the platform refuses it, and the person decides it themselves.
- **A mistake is fixed by pushing the fix.** A run that waits only on removal questions or job approvals gives way to a newer push, so restoring the name and pushing makes the question go away. A developer without approve rights can also mark the resource keep-on-provider on its own page (the guard freed it) and push or redeploy.
- **Removing a whole environment** from the service's configuration is different: the environment's resources keep running (`service.configuring-deployments.md`).

```text
planton service removal destroy checkout-api 131 prod AwsRdsInstance/orders-db   # destroy it: asks at a terminal, --yes answers ahead
planton service removal keep checkout-api 131 prod AwsRdsInstance/orders-db      # keep it on its provider
planton service resolve-env-manual-gate checkout-api 131 prod approve \
  --keep AwsRedisElasticache/orders-cache   # a protected gate: everything it shows and does not keep is destroyed
```

Agents use the same doors: `resolve_service_pipeline_node_gate` (approve destroys the removal its question asks about) and `resolve_service_pipeline_env_gate` with `keep` for a gate's removals, each with `confirm` — passed only on the person's word, never on a run your own person started, and followed by exactly what was destroyed. A gate's approve or a removal's destroy asks at a terminal and names what it destroys; `--yes` answers ahead. Rejecting and keeping ask nothing.

## Every verb answers a dry run

Promote, rollback, redeploy and deploy each take `--dry-run` (API `dry_run`). The verb runs its own steps and refusals, builds the run it would create through the very code that creates one, and prints what that run would apply in its environment, whether it waits at a gate, and every removal — then exits 0 having saved nothing and taken no run number. A refusal the verb would give is given instead. Use it whenever a person asks "what would this do?", and before any delivery into production: say what it removes out loud ("this rollback also destroys search-index in prod"). The console's Promote, Roll Back and Redeploy confirms read the same answer, so a confirm and the run it starts can never disagree.

## Environments that take builds only by promotion

Each Promotion Path names its first Promotion Only stage (`reachedByPromotionFromStage` on the organization's PromotionPathSet). An unscoped run (a trigger-branch push, a tag release, a manual run by commit) walks each path the service's environments sit on, in the order the organization lists its paths: stage by stage, a stage's environments one after another in name order, stopping at that stage. Its environments, and every later stage's, change only when someone promotes a build into them. The run records each of them as skipped with `skip_cause: reached_by_promotion` and `promote_from_env` naming the environment this push deployed that a promotion carries the build from (empty when the push deployed nothing before it on that path; the reason then names the deploy verb); the run page shows that environment Awaiting Promotion with Promote on the strip's step into it (and the service's Delivery Path offers the same step), `planton follow` ends with the exact command (`planton service promote --deployment <svcdepl_...> --to <env>`), and the GitHub check's title says which environments take the build by promotion. This is the design, not a failure: when someone asks why demo or prod did not change after a push, the answer is a promotion, never a re-run. Two other causes are named the same way: `not_on_a_promotion_path` (the environment sits on no path, so a push never guesses where it goes — add it to a path, or deploy the build there) and `driven_by_branch` (a mapped branch deploys it, named in `driving_branch`; the walk leaves it to that branch and goes on). Every skipped environment is still captured, so a later promotion or deploy carries this run's configuration. A run left with nothing to deploy ends **Skipped**, never Succeeded, with a reason naming every cause (`service.reading-a-run.md`). A run skipped at an environment because a newer run got there first carries `skip_cause: superseded_by_newer_run` and names that run in `superseded_by_service_pipeline_id`; promote the newer run's build instead.

A branch mapped (`deploy.branchDeployments`) to an environment in or after its path's Promotion Only stage is refused when the service is saved: the path wins, and the refusal names both.

**A promotion stays on its Promotion Path.** It moves a build between stages of the one path its source and target share, in either direction (bringing an earlier stage level with a hotfixed later one is legitimate). Promoting across two paths, or into or out of an environment on no path, is refused naming both places, and the deploy verb is the way to reach any environment directly. Environments in one stage are siblings: each is promoted on its own, as its own run. `planton service promote` may leave out `--to`: it is then the next stage after the source on the service's Delivery Path — its one environment, or at a terminal the sibling the person chooses; without a terminal, a stage of several is refused with the command to rerun with `--to`.

## Protection is never bypassed

Promoting into a protected environment still stops at that environment's approval gate, and the person who promoted approves it only when no other approver exists. Report the gate and who can resolve it. Approve only on the person's word, and never a run your own person started — even when they are the only approver, the platform refuses it, and they approve it themselves.

## Naming the source of a promotion

Promotion needs to know which deployment moves. Name it one of two ways, never both: the deployment record itself, or the service plus the environment whose current deployment should move. Ambiguity is refused rather than guessed at, because guessing here deploys the wrong version.

Before promoting, read where each environment stands: `get_service_delivery_path` (CLI: `planton service status <service>`) answers each of the service's environments on its Promotion Paths, stage by stage (siblings side by side), then those on no path, with the build it runs, the run that built it, how far it is from what it is measured against ("3 commits behind dev", "Same build as staging": the earlier-stage environment its build was promoted from, else the nearest earlier stage's newest) and the runs moving into it now. Confirm which version is about to move and say the version and the commit out loud in your answer — the person is about to change what production runs. When the target is AHEAD of the source or has diverged from it, promoting replaces newer code: say that before asking.

## The refusals, and what each one means

Each refusal names a real next step. Relay it rather than retrying:

- **The target environment was never prepared for this artifact.** The run that produced this deployment did not resolve configuration for that environment, so there is nothing tested to promote. The fix is to add the environment to the service's deploy environments and push once; that build prepares it.
- **A deployment to that environment is already waiting for approval.** Someone needs to decide on the run that is already there. Starting a second deployment would leave the first waiting forever, so the answer is to surface the pending gate.
- **A deployment to that environment is already in progress.** Wait for it, and follow it.
- **Deployments are turned off for this service.** The switch is deliberate — either the environment is still being prepared, or something outside Planton owns this service's deployment. Do not work around it.
- **The deployment names no artifact**, or **did not record the configuration it applied.** There is nothing to redeploy exactly. Deploy the version you want from a build instead.
- **Promoting into the environment it already runs in.** That is a rollback in place, not a promotion.
- **No push has rendered the kustomize tree onto the record yet** (deploy verb only). A git-maintained service's configuration lands on the record when a branch that drives an environment pushes; until the first such push there is nothing to render from — push to a driving branch (the promotion branch or a mapped one), or promote an existing deployment.
- **The environment is not among the service's declared deploy environments** (deploy verb only). The refusal names the declared set; add the environment to the service's deploy declaration and apply it first.
- **The target is a preview environment** (all four verbs). A preview (`{service}-pr-{n}`) deploys only from its own pull request's pushes — push to the pull request to update its preview, or close it to tear the preview down; deliveries target durable environments. The mirror case refuses too: **promoting FROM a preview's deployment** answers "merge the pull request" (the merge commit builds and deploys through the normal lane), or deploy its image directly with the deploy verb. See `service.preview-environments.md`.
- **The deployment was observed from a GitOps system** (trigger provenance `gitops`). Planton did not perform it — the record is a report of another system's deploy, not a restorable fact — so promote and rollback both refuse, including when "roll back one" lands on an observed record. The real path is the git repository that system watches: the change belongs there, and that system will deliver it. Never advise working around the fence.

## Where a delivery came from

A delivery run carries its origin, stamped at birth, so it never has to be reconstructed:

- **The hop before.** `spec.trigger.source_service_pipeline_id` and `source_run_number` name the run that put the source deployment where it is — the dev deployment's run, for a promotion out of dev. The console reads "Promoted from dev · Run #129". It stays true after dev moves on.
- **The build.** The artifact itself carries the run that built it: `artifact.build_service_pipeline_id` and `build_run_number` ("Built by Run #128"). Promotions and rollbacks copy the artifact, so a prod deployment two promotions away still names its build. Both are empty for an image the deploy verb was handed — no run built it.
- **The deployment record.** `spec.trigger.service_pipeline_run_number` names the run that made each deployment ("Deployed by Run #129").

When someone asks "which build is in prod, and where did it come from?", these three answer it without reading any other run.

## A delivery run is never rerun

Rerunning repeats a build: the new run rebuilds the source run's commit. A promotion, a rollback, a redeploy, or a deploy of an image built nothing, so rerunning one is refused (`planton service rerun`, `rerun_service_pipeline`; the console's run page offers Rerun on build runs only), and the refusal names the verb that repeats it:

```text
Run #129 promoted 'Fix login' from dev to staging; running it again would rebuild the commit instead of promoting it. Promote again: planton service promote checkout-api --from dev --to staging, or Promote on the service's Delivery Path.
```

A rollback's refusal names `planton service rollback <service> --env <env> --to-deployment <svcdepl_…>` (or Roll Back in the service's Deployments); a deploy's names `planton service deploy <service> --env <env> --image <ref>`; a redeploy's reads "Run #131 redeployed what runs in prod; running it again would rebuild the commit instead. Redeploy again: planton service redeploy checkout-api --env prod, or Redeploy in the service's Deployments." Relay it, then offer exactly that verb: a failed promotion is promoted again, never rerun.

## How a delivery run looks while it runs

It is an ordinary run with no build stage: one environment, and the deploy work inside it. Follow it exactly as you would a push-triggered run. If it is parked at an approval gate, the run reports itself as awaiting approval — that is the truth to relay, along with the fact that nothing is executing until a person decides.

What a run of any kind says while it deploys, and how to relay it:

- **"Waiting for Run #127 to finish deploying prod."** An older run of the service is still applying that environment, so this one waits — however long it takes; a newer run never deploys over an older one. When the sentence goes on " Its change to orders-db waits for approval.", the older run waits on a person: the approval moves both runs.
- **"Not run: AwsRdsInstance/orders-db failed"** on a resource means it depends on the resource that failed, so it never started. Fix the failed one; the dependents are not separate failures.
- **A pushed run that gave way** ends its environment naming the newer run of the service that took it. Nothing failed: the newer commit deploys instead.
- **A cancel** answers once the run confirms it, and the run settles on what its jobs really did: a resource whose job finished before the cancel reached it keeps its success, and one whose job outlived the wait reads "Cancel requested; infra job … was still running".

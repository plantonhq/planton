# Kubernetes Agent Substrate

## When NOT to Use This

**One resource is the Agent Substrate CONTROL PLANE**: the API server products create agents through, the identity server that publishes the keys agent tokens are verified with, the controller that turns worker pools into worker pods, the node agent that runs and snapshots agents on each node, the ingress router and egress gateway every agent's traffic crosses, and the pod-certificate controller that signs every component's mTLS. One installation per cluster (an upstream contract).

Not the right kind when:

- **You want capacity to run agents** — that is a worker pool, [`KubernetesAgentSubstrateWorkerPool`](../kubernetesagentsubstrateworkerpool/README.md), its own resource on top of this one: the control plane alone runs no agent. The runtime an agent boots is a [`KubernetesAgentSubstrateSandboxConfig`](../kubernetesagentsubstratesandboxconfig/README.md), and a storage driver for agents' external volumes is a [`KubernetesAgentSubstrateCsiDriverConfig`](../kubernetesagentsubstratecsidriverconfig/README.md).
- **You want a sandbox per user session, with no suspend and resume** — [`KubernetesAgentSandboxController`](../kubernetesagentsandboxcontroller/README.md) and its sandbox kinds give each agent a pod of its own; Agent Substrate earns its place when most agents sit idle and should cost nothing until a request wakes them.
- **Your cluster cannot serve the pod-certificate APIs** — Substrate needs Kubernetes' PodCertificateRequest and ClusterTrustBundle APIs. On GKE they must be enabled when the cluster is created (GKE 1.36 with the beta APIs, or 1.37); there is no way to add them to a running cluster.

## Generated secrets

The five certificate authorities behind Substrate's mTLS, actor identities and egress interception, and the key that signs actor tokens, are generated by the module in upstream's exact format and kept in the deployment's state. A re-apply never replaces them; a destroy does, exactly like an upstream reinstall. The authorities last ten years rather than upstream's one, because every connection that chains to an expired root fails, and a module that re-issued an expired root would rotate trust out from under every certificate already issued.

## Upgrades refuse what Substrate cannot survive

The API server migrates its database schema forward irreversibly on its first start, so Substrate upgrades one minor release at a time, rolls back at most one, and reinstalls across a major; before 1.0 every minor release was a reinstall, so a v0.x installation reinstalls to reach v1.0. The module stamps the installed release on the API server and the minor that wrote the bundled database on its volume (which outlives a destroy while another resource owns the namespace), and refuses at plan time an apply that breaks that rule, with the backup, destroy and clear steps that move it safely.

## Distribution and the version

Agent Substrate publishes its release images (`ghcr.io/agent-substrate/substrate`) but no installable release. Planton publishes one for each upstream release: upstream's manifests with every image pinned by the digest upstream's registry serves, immutable, at `https://downloads.planton.ai/releases/agent-substrate/<version>/`. The module composes that tree the way upstream's installer does, applies the typed settings onto upstream's own objects, and takes the resource definitions through the kept-definition path.

The modules compose one install shape, v1.0.0's, and `version` picks any release Planton publishes with that shape: one whose install differs only in its images, which Planton proves before it publishes. So an upstream patch reaches you by setting `version`, with no catalog update. A release of another shape, or one Planton has not published, is refused before anything is applied; every file read is checked against the release's checksums. The catalog's Substrate kinds mirror the shape's definitions.

# AzureKeyVaultCertificate Pulumi Module

## Overview

This Pulumi module provisions an X.509 certificate inside an Azure Key
Vault using the Azure Classic provider (`pulumi-azure`). It creates a
single `keyvault.Certificate` -- a DATA-PLANE object: the provider talks to
the vault's `{name}.vault.azure.net` endpoint, not ARM, so the deploying
credential needs data-plane certificate permissions on the vault even if it
owns the subscription -- the full deployer grant set is cataloged in
[`../permissions.yaml`](../permissions.yaml).

The certificate can be GENERATED by the vault (self-signed or CA-issued,
from `certificate_policy`) or IMPORTED from an existing PFX/PEM bundle
(`certificate`) -- or both, when an import carries an explicit governing
policy. Enrollment against issuer "Self" completes synchronously; a CA
issuer keeps the operation pending until the CA responds.

## Resources Created

- `keyvault.Certificate` -- the certificate with its three faces
  (certificate, private key, secret bundle)

## Inputs

The module receives an `AzureKeyVaultCertificateIacInput` containing:

- `target.spec.name` -- 1-127 letters/digits/hyphens, unique among the vault's certificates
- `target.spec.key_vault_id` -- the vault's ARM ID (resolved from an AzureKeyVault reference by the platform)
- `target.spec.certificate` -- the import path: base64 `contents` + optional `password` (both sensitive -- the bundle carries the private key); changing contents imports a new VERSION
- `target.spec.certificate_policy` -- the generate/govern path: `issuer_name` ("Self"/"Unknown"/CA issuer name), `key_properties` (type/size/curve translated through exhaustive vocabularies; `oct` included for API completeness), `lifetime_actions` (AutoRenew/EmailContacts with exactly one trigger each), `secret_properties.content_type` (PKCS12/PEM translated to the `application/x-pkcs12` / `application/x-pem-file` media types), and `x509_certificate_properties` (subject, SANs, lowerCamel key usages, EKU OIDs, validity)
- `target.spec.tags` -- user tags, merged over the metadata-derived tags (user wins)
- `provider_config` -- Azure credentials (static client secret, keyless web identity, or ambient chain)

Everything in the policy except `lifetime_actions` creates a new
certificate version when changed; lifetime actions update in place.

## Outputs

| Output | Description |
|--------|-------------|
| `certificate_id` / `versionless_id` | Data-plane IDs (versioned / renewal-following) |
| `secret_id` / `versionless_secret_id` | The secret face -- what TLS terminators consume |
| `certificate_name` / `version` | Name and current version |
| `thumbprint` | SHA-1 fingerprint |
| `resource_manager_id` / `resource_manager_versionless_id` | ARM (control-plane) IDs |

## Operational Notes

- A deleted certificate's name stays reserved in the vault for the
  soft-delete retention window; the provider's default features purge
  soft-deleted certificates on destroy so the name frees up immediately.
- Renewals mint a new version (fresh private key unless `reuse_key` is
  true); consumers on the versionless references follow automatically.
